CHAPTER 01

Why pandas exists

NumPy gave you fast arrays. Pandas gives you arrays with names — and once your data has names, every operation reads like English.

NumPy is brilliant for math, but it has one problem for real data: every dimension is just a position. The seventh column has no name. The fifteenth row has no identity. If you ever need to track "what does column 4 represent" or "match these customer IDs to those order IDs," you're back to managing index lookups by hand. Pandas solves this by adding labels — every row has an index, every column has a name — and once that's true, alignment, joining, grouping, and reshaping all become natural.

1.1The two core data structures

The whole library is built on two objects:

  • Series — a one-dimensional labeled array. Think "a column with a name and a row index."
  • DataFrame — a two-dimensional labeled table. Think "a dict of Series sharing the same row index."

Everything else — groupby, merge, pivot — is operations on these two. Get the data model right and the rest follows.

1.2The right altitude

Pandas sits between NumPy and SQL in a useful way:

ToolStrengthPain point
NumPyfastest math on dense arraysno labels, no missing values, no mixed types
Pandaslabeled tables, mixed types, missing data, joins, groupbyslower than NumPy, less scalable than Spark/Polars
SQLscales, transactional, declarativeverbose for analysis, no native ML integration
Spark / Polarsbillions of rows, distributedmore ceremony for small-to-medium data

For datasets up to maybe 10 GB on a single machine, pandas is usually the right answer. Anything smaller and the alternatives are overkill; anything larger and you'll outgrow it.

1.3Installing and importing

# Bash
pip install pandas pyarrow      # pyarrow is the modern backend

# Python — the universal convention
import pandas as pd
pd.__version__

Like np, the pd alias is everywhere — never alias it differently. Modern pandas (2.x) defaults to NumPy-backed arrays but works much better when you also have pyarrow installed for IO speed and string handling.

1.4The mental model

Think of a DataFrame as a spreadsheet with one extra rule: every row has a label (the index) and every column has a name. All operations respect those labels. When you add two DataFrames, pandas aligns by labels first, not by position. When you join, you join on labels. When you group, you group by labels. Labels are the entire game.

Where you'll meet pandas

Every Jupyter notebook with tabular data. Every ML pipeline before the matrix goes into scikit-learn. Every dashboard built on Python. Every ETL job that doesn't yet run in Spark. Every data scientist's day. Pandas is the lingua franca of Python data work — and learning it once pays off forever.

2.4Vectorized operations

Like NumPy arrays, Series operations are vectorized:

prices = pd.Series({"apple": 1.5, "orange": 2.0, "pear": 3.0})
qty    = pd.Series({"apple": 10, "orange": 5, "pear": 2})

revenue = prices * qty
revenue
apple     15.0
orange    10.0
pear       6.0
dtype: float64

2.5The killer feature — alignment by index

When you combine two Series, pandas aligns them by label, not by position. Mismatched labels produce NaN.

a = pd.Series({"x": 1, "y": 2, "z": 3})
b = pd.Series({"y": 10, "z": 20, "w": 30})
a + b
w     NaN
x     NaN
y    12.0
z    23.0
dtype: float64

Notice: y and z are added correctly (12 = 2+10, 23 = 3+20). The label x exists only in a, w only in b — both become NaN. This is the source of pandas' magic and also its most common gotcha.

remember

Position is for code that's wrong. Labels are for code that's right. The whole point of pandas is that you can rearrange, filter, and combine data and still trust that "row labeled customer_42 is in fact customer 42's row." NumPy can't promise that.

2.6Useful Series methods

s = pd.Series([3, 1, 4, 1, 5, 9, 2])

s.describe()                  # count, mean, std, min, quartiles, max
s.value_counts()               # frequencies — sorted
s.unique()                     # unique values, order preserved
s.nunique()                    # count of unique values
s.sort_values()                # sort by value
s.sort_index()                 # sort by index label
s.isin([1, 2])                 # boolean mask: is each value in [1, 2]?
Application

A Series is the unit of pandas thinking. When you select a column from a DataFrame, you get a Series. When you call .mean(), you reduce a Series to a scalar. When you call .value_counts(), you produce a Series. Most of "doing pandas" is composing Series operations. Get comfortable here and DataFrames become obvious.

Loading data

Most data work starts with read_csv and a stubborn file. Knowing the options makes the difference between five seconds and five hours.

4.1CSV — the workhorse

df = pd.read_csv("sales.csv")

prefer parquet

For anything you'll re-read more than once, save it as Parquet. It's typed (no string-int confusion on reload), compressed (often 5-10× smaller than CSV), and reads 10-100× faster. df.to_parquet("file.parquet") is your friend.

4.4Writing data

df.to_csv("out.csv", index=False)            # index=False unless you mean it
df.to_parquet("out.parquet")
df.to_excel("out.xlsx", sheet_name="results")
df.to_json("out.json", orient="records")
index=False

Default to_csv writes the row index as the first column. If your index is just 0, 1, 2, ... (which it usually is), pass index=False or your file gains a useless column on every save. The number of CSVs in the wild with a stray "Unnamed: 0" column is staggering.

Application

Half of "data engineering" is reading files. Master the read_csv arguments and you eliminate the most frustrating class of pandas bugs — the ones where your data loaded "successfully" but the numbers are strings, the dates aren't dates, and your aggregations silently produce garbage.

CHAPTER 05

Selection & indexing

Pulling out specific rows and columns. The simplest pandas operation, with the most confusing API. This chapter unconfuses it.

5.1The three selection styles

df = pd.DataFrame({
    "name":    ["Alice", "Bob", "Carol", "Dan"],
    "age":     [25, 32, 28, 45],
    "city":    ["Austin", "Dallas", "Houston", "Austin"],
    "salary":  [75000, 92000, 68000, 120000],
})

1 · Bracket — for columns

df["age"]                  # single column → Series
df[["name", "age"]]         # multiple columns → DataFrame
df[0:2]                    # slice rows by position

2 · .loc — label-based

df.loc[0]                  # row at label 0
df.loc[0, "name"]          # single cell
df.loc[0:2, "name":"city"]   # inclusive slices — both ends!
df.loc[df["age"] > 30]      # boolean mask

3 · .iloc — position-based

df.iloc[0]                 # first row (regardless of index label)
df.iloc[0:2, 0:2]          # top-left 2×2 — exclusive at end
df.iloc[-1]                # last row
the rule

loc is inclusive, iloc is exclusive on the right end of a slice. df.loc[0:2] returns rows 0, 1, AND 2. df.iloc[0:2] returns rows at positions 0 and 1 only. This catches everyone the first time.

5.2Boolean masking — the workhorse

df[df["age"] > 30]                              # filter rows
df[df["city"] == "Austin"]
df[df["city"].isin(["Austin", "Dallas"])]      # multiple values

# Combined conditions — & | ~, ALWAYS parenthesized
df[(df["age"] > 25) & (df["city"] == "Austin")]
df[(df["age"] < 30) | (df["salary"] > 100000)]
df[~(df["city"] == "Austin")]                    # negate
parentheses

Always parenthesize each comparison. df[df.age > 25 & df.city == "Austin"] is wrong because & binds tighter than >. Write df[(df.age > 25) & (df.city == "Austin")] and never wonder again.

5.3query — readable filtering

For complex filters, query is much more readable:

df.query("age > 25 and city == 'Austin'")
df.query("salary > @threshold")               # @ references Python variables

5.4Setting values

df.loc[df["city"] == "Austin", "salary"] *= 1.05   # 5% raise for Austin
df.loc[0, "age"] = 26                            # single cell
df.loc[df["age"] > 100, "age"] = np.nan             # bulk set

5.5SettingWithCopyWarning — what it actually means

The single most-Googled pandas error. It means: you might be modifying a copy instead of the original.

# Bad — ambiguous
subset = df[df["age"] > 30]
subset["salary"] = 0                              # SettingWithCopyWarning!

# Good — modify the original
df.loc[df["age"] > 30, "salary"] = 0

# Or — explicitly make a copy you want to modify
subset = df[df["age"] > 30].copy()
subset["salary"] = 0
the rule

If you want to modify a slice, use df.loc[mask, "col"] = value in one statement. If you want to keep a copy separately, call .copy() explicitly. The warning goes away forever.

Application

Selection is the bread of pandas work. Every dashboard query is "give me rows where X and aggregate Y by Z." Every cleaning operation is "find rows that look wrong and fix them." Boolean masks and .loc assignment together handle ~80% of all real pandas code you'll write.

CHAPTER 06

Cleaning data

Real data is messy. Missing values, wrong types, duplicates, inconsistent strings. Half your job is making it usable.

6.1Finding missing values

df.isna()                  # boolean DataFrame: True where missing
df.isna().sum()            # count missing per column — your first move
df.isna().mean()           # fraction missing per column
df[df["col"].isna()]        # rows where col is NaN
df.notna()                 # opposite of isna

6.2Handling missing values — three options

# 1. Drop
df.dropna()                                # drop any row with any NaN
df.dropna(subset=["price", "qty"])           # only check these
df.dropna(thresh=3)                       # keep rows with ≥3 non-null values

# 2. Fill
df.fillna(0)                                # fill all NaN with 0
df["price"].fillna(df["price"].median())     # fill with median
df.fillna(method="ffill")                  # forward-fill from previous row
df.fillna(method="bfill")                  # back-fill from next row

# 3. Interpolate (numeric only)
df["price"].interpolate()                  # linear interpolation

6.3Type coercion

df["price"] = df["price"].astype("float64")
df["id"]    = df["id"].astype("int32")
df["date"]  = pd.to_datetime(df["date"])
df["num"]   = pd.to_numeric(df["num"], errors="coerce")   # bad → NaN
df["cat"]   = df["cat"].astype("category")               # much smaller for repeated strings

The errors="coerce" trick is invaluable — it turns unparseable values into NaN instead of raising. Combine with fillna to handle them.

6.4Duplicates

df.duplicated()                          # mark duplicate rows (after first)
df.duplicated(subset=["customer_id"])    # only check these columns
df.drop_duplicates()                     # keep first occurrence
df.drop_duplicates(subset=["id"], keep="last")   # keep last instead

6.5String cleanup — the .str accessor

Every Series of strings has a .str accessor exposing vectorized string methods:

df["name"] = df["name"].str.strip()           # trim whitespace
df["name"] = df["name"].str.lower()           # lowercase
df["name"] = df["name"].str.title()           # Title Case
df["name"] = df["name"].str.replace("-", " ")
df["email"].str.contains("@gmail", na=False)
df["phone"].str.extract(r"(\d{3})-(\d{3})-(\d{4})")  # regex groups
df["city"].str.split(",", expand=True)         # split into cols

6.6Renaming columns

df.rename(columns={"old_name": "new_name"}, inplace=True)
df.columns = [c.lower().replace(" ", "_") for c in df.columns]   # bulk clean
Application

The first 30 minutes with any new dataset go to cleaning. The pattern: df.info() → identify problems → fix them one by one. Always assign cleaned data back to a new variable or to the same DataFrame deliberately — never lose track of what you've changed.

CHAPTER 07

GroupBy deep dive

Split the data by key, apply something to each group, combine the results. Three steps that handle a huge share of all data analysis you'll ever do.

GroupBy is the conceptual heart of pandas. Every "total sales per region," "average price per category," "max temperature per month" is a groupby. It's named after the SQL GROUP BY clause but does much more — you can apply any function, not just sum or mean. Master this chapter and you've mastered most of pandas.

7.1Split-apply-combine

Figure 7.1Split-apply-combine. The rows are partitioned by group key, a function runs on each partition, and the results are stitched back into a single output.

7.2The basic pattern

df = pd.DataFrame({
    "region":  ["East", "West", "East", "South", "West", "East"],
    "product": ["A", "A", "B", "A", "B", "A"],
    "sales":   [100, 150, 200, 80, 130, 90],
    "units":   [10, 15, 18, 8, 12, 9],
})

df.groupby("region")["sales"].sum()
region
East     390
South     80
West     280
Name: sales, dtype: int64

Three pieces: the grouper ("region"), the column to operate on ("sales"), and the aggregation (.sum()). Variations on this single pattern do the heavy lifting in pandas.

7.3Multiple aggregations at once

df.groupby("region")["sales"].agg(["sum", "mean", "max", "count"])
        sum        mean  max  count
region
East    390  130.000000  200      3
South    80   80.000000   80      1
West    280  140.000000  150      2

7.4Different aggregations per column — the agg dict

df.groupby("region").agg({
    "sales": ["sum", "mean"],
    "units": "max",
})

7.5Named aggregations — the cleanest output

df.groupby("region").agg(
    total_sales=("sales", "sum"),
    avg_sales=("sales", "mean"),
    n_orders=("sales", "count"),
    total_units=("units", "sum"),
)
        total_sales   avg_sales  n_orders  total_units
region
East            390  130.000000         3           37
South            80   80.000000         1            8
West            280  140.000000         2           27

Named aggregations give clean column names with no multi-index gymnastics. This is the modern recommended pattern.

7.6Multi-column groupby

df.groupby(["region", "product"])["sales"].sum()
region  product
East    A          190
        B          200
South   A           80
West    A          150
        B          130
Name: sales, dtype: int64

The result has a multi-index. Often you want flat columns instead:

df.groupby(["region", "product"], as_index=False)["sales"].sum()
  region product  sales
0   East       A    190
1   East       B    200
2  South       A     80
3   West       A    150
4   West       B    130

7.7transform — same shape as input

agg reduces each group to one row. transform instead spreads the result back to every row of the original — perfect for "add a per-group column to the original DataFrame":

df["region_total"] = df.groupby("region")["sales"].transform("sum")
df["share_of_region"] = df["sales"] / df["region_total"]
df
  region product  sales  units  region_total  share_of_region
0   East       A    100     10           390         0.256410
1   West       A    150     15           280         0.535714
2   East       B    200     18           390         0.512821
3  South       A     80      8            80         1.000000
4   West       B    130     12           280         0.464286
5   East       A     90      9           390         0.230769
agg vs transform

Reduce each group to one number per group → agg. Compute a per-group value but keep every original row → transform. The mental model: agg shrinks, transform broadcasts. Once you internalize this, complex pandas code becomes obvious.

7.8filter — keep or drop whole groups

# Keep only regions with more than 2 orders
df.groupby("region").filter(lambda g: len(g) > 2)

7.9apply — the escape hatch

For anything agg and transform can't express, apply runs a user function on each group:

# Top-2 sales rows per region
df.groupby("region").apply(lambda g: g.nlargest(2, "sales"))

Powerful but slower than agg/transform. Reach for apply last, not first.

7.10Common patterns

# Counting
df.groupby("region").size()                       # rows per group
df["region"].value_counts()                       # shortcut for one column

# Multiple aggregations, flat output
(df.groupby("region")
   .agg(total=("sales", "sum"), avg=("sales", "mean"))
   .reset_index())

# Rank within group
df["rank_in_region"] = df.groupby("region")["sales"].rank(ascending=False)

# Cumulative within group
df["running_total"] = df.groupby("region")["sales"].cumsum()

# Percent change within group
df["pct_change"] = df.groupby("region")["sales"].pct_change()
Application

If you do one thing well in pandas, make it groupby. "Per customer," "per day," "per category" — any business question ends in a groupby. Combine groupby with the transform trick and you've replaced thousands of lines of SQL window-function code with three lines of Python.

CHAPTER 08

Merging & joining

Combining two DataFrames into one. SQL joins for Python, with extra superpowers from the labeled index.

8.1Two flavors — concat vs merge

Two distinct operations:

  • concat — stack DataFrames together, top-to-bottom (rows) or side-by-side (columns). Pure stacking, no matching by key.
  • merge — match rows from two DataFrames based on shared key columns. Like SQL JOIN.

8.2concat — pure stacking

a = pd.DataFrame({"x": [1, 2], "y": [10, 20]})
b = pd.DataFrame({"x": [3, 4], "y": [30, 40]})

pd.concat([a, b])                  # stack vertically (along axis=0)
pd.concat([a, b], ignore_index=True)  # renumber the index
pd.concat([a, b], axis=1)         # stack horizontally
   x   y
0  1  10
1  2  20
0  3  30
1  4  40
# with ignore_index=True, the index becomes 0,1,2,3

8.3merge — match by key

customers = pd.DataFrame({
    "customer_id": [1, 2, 3],
    "name":        ["Alice", "Bob", "Carol"],
})

orders = pd.DataFrame({
    "order_id":    [100, 101, 102, 103],
    "customer_id": [1, 2, 2, 4],
    "amount":      [50, 100, 75, 200],
})

orders.merge(customers, on="customer_id")
   order_id  customer_id  amount   name
0       100            1      50  Alice
1       101            2     100    Bob
2       102            2      75    Bob

By default, merge does an inner join: only rows present in both. Customer 3 has no orders → dropped. Order 103 has no matching customer → dropped.

8.4The four join types

Figure 8.1The four join types. Inner keeps only matched rows. Left keeps every left row, filling NaN for unmatched. Right mirrors left. Outer keeps everything, NaN where one side is missing.
orders.merge(customers, on="customer_id", how="inner")
orders.merge(customers, on="customer_id", how="left")
orders.merge(customers, on="customer_id", how="right")
orders.merge(customers, on="customer_id", how="outer")

Left join — most common in practice

orders.merge(customers, on="customer_id", how="left")
   order_id  customer_id  amount   name
0       100            1      50  Alice
1       101            2     100    Bob
2       102            2      75    Bob
3       103            4     200    NaN

Order 103's customer doesn't exist in the customers table — but the row stays, name becomes NaN. This is what you usually want: keep your "main" table intact, attach lookup info where available.

8.5Different key names — left_on / right_on

orders.merge(customers, left_on="customer_id", right_on="id")

8.6Merging on the index

customers_indexed = customers.set_index("customer_id")
orders.merge(customers_indexed, left_on="customer_id", right_index=True)

# Shortcut when both sides are indexed
orders.join(customers_indexed, on="customer_id")

8.7The validate parameter — your safety net

The single most important argument no one uses. Tell merge what kind of relationship to expect — it errors if your data violates it.

orders.merge(customers, on="customer_id", validate="many_to_one")
# raises if customer_id is not unique in customers
validateMeans
"one_to_one"both sides have unique keys
"one_to_many"left is unique, right may repeat
"many_to_one"right is unique, left may repeat (lookup table — common)
"many_to_many"both may repeat (explicit cartesian — be careful)
silent bugs

If your "lookup" table accidentally has duplicate keys, an unguarded merge will silently multiply your rows — and you may not notice until totals are wrong. validate="many_to_one" catches this at the source. Always pass it.

8.8Suffixes — same column name on both sides

left.merge(right, on="id", suffixes=("_2023", "_2024"))
# columns named "revenue" on both sides → revenue_2023, revenue_2024

8.9indicator — see where each row came from

orders.merge(customers, on="customer_id", how="outer", indicator=True)
   order_id  customer_id  amount   name      _merge
0     100.0            1    50.0  Alice        both
1     101.0            2   100.0    Bob        both
2     102.0            2    75.0    Bob        both
3     103.0            4   200.0    NaN   left_only
4       NaN            3     NaN  Carol  right_only

The _merge column tells you whether each row was in left, right, or both. Indispensable for debugging join mismatches.

Application

The four merge skills that handle 95% of real joins: left join with validate="many_to_one" when attaching lookup info, inner join when only matched rows matter, indicator=True when you can't figure out why row counts are wrong, and suffixes when both sides have a column with the same name. Master these and you'll never write "double-counted by accident" in a post-mortem again.

CHAPTER 09

Reshape

Same data, different shape. Wide vs long. The transformation that makes the difference between "I can plot this" and "I cannot."

9.1Long vs wide — the foundational concept

The same data can be stored two ways:

Figure 9.1Same six observations, two shapes. Long stores each measurement as a row — great for storage and statistical models. Wide spreads one variable across columns — easier for human reading and many plotting libraries.

9.2pivot — long to wide

sales = pd.DataFrame({
    "region":  ["East", "East", "West", "West", "South", "South"],
    "product": ["A", "B", "A", "B", "A", "B"],
    "sales":   [100, 200, 150, 130, 80, 110],
})

sales.pivot(index="region", columns="product", values="sales")
product    A    B
region
East     100  200
South     80  110
West     150  130

Three arguments: index becomes the new row labels, columns becomes the new column labels, values fills the cells. The original DataFrame must have unique combinations of (index, columns) — pivot can't decide which value wins on duplicates.

9.3pivot_table — pivot with aggregation

When you have duplicates and want to aggregate them, use pivot_table:

sales.pivot_table(
    index="region",
    columns="product",
    values="sales",
    aggfunc="sum",       # or "mean", "count", or any callable
    fill_value=0,         # NaN → 0 in the result
    margins=True,         # add row/column totals
)

9.4melt — wide to long

The inverse of pivot. Take "wide" data and stack the columns into rows:

wide = pd.DataFrame({
    "region": ["East", "West", "South"],
    "A": [100, 150, 80],
    "B": [200, 130, 110],
})

wide.melt(
    id_vars="region",       # keep as-is
    var_name="product",     # new col name for the old column names
    value_name="sales",     # new col name for the values
)
  region product  sales
0   East       A    100
1   West       A    150
2  South       A     80
3   East       B    200
4   West       B    130
5  South       B    110

9.5stack and unstack — pivot for multi-index

When working with multi-indexed data, stack and unstack move levels between rows and columns:

multi = sales.set_index(["region", "product"])["sales"]
multi
region  product
East    A          100
        B          200
West    A          150
        B          130
South   A           80
        B          110

multi.unstack()                  # last level → columns
product    A    B
region

multi.unstack("region")          # move a named level instead
multi.unstack().stack()          # round-trip back to original

9.6crosstab — cross-tabulation

A specialized pivot_table for counting:

pd.crosstab(sales["region"], sales["product"])
pd.crosstab(sales["region"], sales["product"], values=sales["sales"], aggfunc="sum")
pd.crosstab(sales["region"], sales["product"], normalize="index")   # row percentages

TaskUse

Application

Reshape is what bridges the gap between "data in the format it's stored" and "data in the format your tool needs." Most plotting libraries (seaborn, plotly) want long format. Most spreadsheet humans want wide format. Most ML pipelines want either, depending on the model. Knowing reshape fluently means you stop fighting your data and start using it.

CHAPTER 10

Apply, transform, and friends

When the built-in operations don't cover what you need. And — just as important — when they actually do, even though it doesn't look like it.

10.1The "stop using apply" hierarchy

Pandas has a culture problem: people reach for apply too quickly. It's slow because it dispatches to Python for every row. Almost always there's a faster vectorized way. Climb this ladder, top down:

  1. Vectorized arithmetic on whole columns — fastest, e.g. df["c"] = df["a"] + df["b"]
  2. Built-in pandas methods — .str, .dt, .fillna, .replace, .where, .clip
  3. np.where / np.select — for branching logic
  4. Series.map(dict) — for value substitution
  5. apply — only when none of the above work

10.2The apply API

df = pd.DataFrame({"x": [1, 2, 3], "y": [10, 20, 30]})

# On a Series — function called on each value
df["x"].apply(lambda v: v ** 2)

# On a DataFrame — function called on each column (default)
df.apply(np.sum)                          # sum of each column

# Row-wise — axis=1
df.apply(lambda row: row["x"] * row["y"], axis=1)

10.3The replacements that beat apply

For arithmetic — just operate on columns

# Slow
df["product"] = df.apply(lambda r: r["x"] * r["y"], axis=1)

# 100× faster
df["product"] = df["x"] * df["y"]

For branching — use np.where

# Slow
df["category"] = df["x"].apply(lambda v: "big" if v > 2 else "small")

# Fast
df["category"] = np.where(df["x"] > 2, "big", "small")

For value mapping — use map

country_map = {"US": "North America", "CA": "North America", "DE": "Europe"}
df["region"] = df["country"].map(country_map)

For string operations — use .str

# Slow
df["clean"] = df["name"].apply(lambda s: s.strip().lower())

# Fast
df["clean"] = df["name"].str.strip().str.lower()

10.4When apply is genuinely needed

Some real cases where apply is the right answer:

# 1. Calling an external function that takes a row
def classify_transaction(row):
    if row["amount"] > 10000 and row["country"] in SUSPICIOUS:
        return "flag"
    return "ok"

df["label"] = df.apply(classify_transaction, axis=1)

# 2. apply on a GroupBy — most common legitimate use
df.groupby("customer").apply(lambda g: g.nlargest(3, "amount"))

# 3. Calling an API or a model per row
df["sentiment"] = df["text"].apply(call_sentiment_api)
the test

Before writing apply, ask: can I express this with column arithmetic, a built-in method, np.where, or .map? If yes — use that. Apply is the escape hatch, not the default tool.

10.5Method chaining — pipelines that read top-to-bottom

result = (
    df
    .query("amount > 0")
    .assign(month=lambda d: d["date"].dt.month)
    .groupby(["region", "month"])
    .agg(total=("amount", "sum"), n=("amount", "count"))
    .reset_index()
    .sort_values("total", ascending=False)
)

Each line is a small step. The data flows top-to-bottom. No intermediate variables. This is how mature pandas code looks — the dplyr-style chained pipeline.

Application

Method chaining changes how you write pandas. Instead of df = ...; df = ...; df = ... with a dozen reassignments, you express the whole transformation as one expression. Easier to read, easier to debug (comment out a line to see the intermediate result), and harder to leak stale state.

11.5resample — groupby for time

daily = ts                                  # daily values

daily.resample("W").mean()                  # weekly mean
daily.resample("QE").agg(["sum", "mean", "std"])

# Upsampling — go from less to more frequent

# Exponentially weighted
ts.ewm(span=7).mean()                          # EWMA — more weight on recent

Application

For any time-indexed data — sales, sensor readings, server metrics — these tools handle 95% of the work. Resample to the right granularity, compute rolling averages to smooth noise, use shift/diff to compute deltas. Pandas turns a week of time-series analysis into a single afternoon.

CHAPTER 12

Performance

Pandas is fast until it isn't. Five techniques keep it fast — and tell you when it's time to graduate to Polars or DuckDB.

12.1Check memory usage

df.info(memory_usage="deep")               # includes string memory
df.memory_usage(deep=True).sum() / 1e9     # GB

12.2Downcast numeric types

df["id"] = pd.to_numeric(df["id"], downcast="integer")        # int64 → int8/16/32 if safe
df["price"] = pd.to_numeric(df["price"], downcast="float")    # float64 → float32

Downcasting often cuts memory by 50-75% with zero quality loss.

12.3Use categoricals for repeated strings

df["country"] = df["country"].astype("category")
# a column of 10M strings repeating from 200 unique values
# goes from ~600 MB to ~10 MB. 60× saving.

Categoricals also speed up groupby and merge on those columns.

12.4Chunked reading

for chunk in pd.read_csv("huge.csv", chunksize=100_000):
    process(chunk)                       # aggregate, filter, write to parquet

When the file doesn't fit in memory, process it piece by piece. Often the final result does fit, even when the raw data doesn't.

12.5Vectorize, don't iterate

# Slow — 100× to 1000× slower
for i in df.index:
    df.loc[i, "total"] = df.loc[i, "qty"] * df.loc[i, "price"]

# Fast
df["total"] = df["qty"] * df["price"]

The number-one pandas anti-pattern is iterating over rows with a for loop. Almost always there's a vectorized alternative — find it.

12.6When to leave pandas

SymptomConsider
Memory errors loading dataPolars (book 3), DuckDB, or chunked reading
Operations take minutesPolars (often 5-30× faster on the same machine)
Data is in many filesDuckDB queries directly across parquet files
Need distributed computeSpark (PySpark or Spark SQL)
Need GPU accelerationcuDF (RAPIDS) — pandas-compatible API on GPU
Application

The pragmatic threshold: pandas comfortably handles 1-10 GB on a 32 GB machine. Below 1 GB, never even think about performance. Above 10 GB, your time is better spent learning Polars (the next book) than tuning pandas. There's a sweet spot in the middle — and the techniques above keep you in it.

CHAPTER 13

End-to-end example

A realistic sales pipeline that uses everything in the book. Thirty lines of pandas, one coherent story.

13.1The task

Three CSVs: orders, customers, and products. Build a report of "top 5 customers by revenue per region in Q3 2024, with their favorite product."

import pandas as pd

# ---------- 1. Load ----------
orders = pd.read_csv("orders.csv", parse_dates=["order_date"])
customers = pd.read_csv("customers.csv")
products = pd.read_csv("products.csv")

# ---------- 2. Clean ----------
orders = orders.dropna(subset=["customer_id", "product_id"])
orders = orders.query("amount > 0")
customers["region"] = customers["region"].str.strip().str.title()

# ---------- 3. Join (with safety checks) ----------
df = (
    orders
    .merge(customers, on="customer_id", how="left", validate="many_to_one")
    .merge(products,  on="product_id",  how="left", validate="many_to_one")
)

# ---------- 4. Filter to Q3 2024 ----------
mask = (df["order_date"] >= "2024-07-01") & (df["order_date"] < "2024-10-01")
q3 = df.loc[mask].copy()

# ---------- 5. Revenue per customer ----------
per_customer = (
    q3.groupby(["region", "customer_id", "customer_name"], as_index=False)
      .agg(revenue=("amount", "sum"),
           n_orders=("order_id", "count"))
)

# ---------- 6. Each customer's favorite product ----------
favorite = (
    q3.groupby(["customer_id", "product_name"])["amount"].sum()
      .reset_index()
      .sort_values(["customer_id", "amount"], ascending=[True, False])
      .drop_duplicates(subset="customer_id", keep="first")
      .rename(columns={"product_name": "favorite_product"})
      [["customer_id", "favorite_product"]]
)

per_customer = per_customer.merge(favorite, on="customer_id", how="left")

# ---------- 7. Top 5 per region ----------
top5 = (
    per_customer
    .sort_values(["region", "revenue"], ascending=[True, False])
    .groupby("region")
    .head(5)
    .reset_index(drop=True)
)

# ---------- 8. Save ----------
top5.to_csv("top5_q3_2024.csv", index=False)
top5.to_parquet("top5_q3_2024.parquet")

13.2What this used

  • Loading (Ch 4) — parse_dates argument
  • Cleaning (Ch 6) — dropna, .str methods, query
  • Selection (Ch 5) — boolean masking, .loc, .copy
  • Merging (Ch 8) — left joins with validate
  • GroupBy (Ch 7) — named aggregations, groupby + head pattern
  • Method chaining (Ch 10) — pipelines that read top-to-bottom

13.3What to do next

You now know pandas well enough to be productive on real datasets. To go from "knows" to "fluent":

  1. Write more chains. Resist the urge to create intermediate df1, df2, df3 variables. Chain operations until they don't fit in your head — then start a new chain.
  2. Read the docs index page. Pandas has dozens of useful methods you haven't met yet. Skimming pd.DataFrame. in a Jupyter cell and tab-completing is a productive afternoon.
  3. Move on to Polars. Once pandas feels natural, Polars will feel better — same patterns, much faster, cleaner API. Book 3 picks up from here.
parting word

Pandas will be the tool you reach for most days of your data career. It's not the fastest, not the prettiest, and not always the best — but it's the one with the deepest ecosystem and the strongest hold on the Python data world. Learn it well; the investment compounds for years.
