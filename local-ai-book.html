Part I

Ollama

Run language models on your own machine. No API keys, no cloud bills, no data leaving your laptop.

CHAPTER 01

What is Ollama, and why local?

Ollama is what Docker was to containers: it took something powerful but fiddly and made it a single command.

Before Ollama, running an open-source language model locally meant downloading multi-gigabyte weight files, building llama.cpp from source, finding the right quantization, writing a Python wrapper, and praying your GPU drivers cooperated. After Ollama, it's ollama run llama3.2. The model downloads itself, the runtime starts automatically, and a chat interface appears in your terminal. The barrier dropped from "weekend project" to "thirty seconds."

1.1What Ollama actually is

Three things wrapped together:

  • A model registry — like Docker Hub for LLMs. You can ollama pull llama3.2 and get the right weights, tokenizer, and default settings.
  • A local inference server — runs on http://localhost:11434, exposing an HTTP API. Everything in this book talks to that server.
  • A command-line client — for chatting in the terminal, listing installed models, and managing storage.

1.2Why run models locally

ReasonWhat it means in practice
PrivacyYour prompts and documents never leave the machine. Indispensable for sensitive company data, legal documents, medical records.
CostZero per-token cost. Build a RAG system that ingests a million-page archive and you pay only for electricity.
LatencyNo round trip to a cloud API. First token in 100ms on consumer hardware.
OfflineWorks on planes, in airgapped networks, in places with no internet.
No rate limitsFire as many requests as your hardware can handle.
ReproducibilityThe model file doesn't silently upgrade overnight. Your evals stay valid.

1.3What local models are not good at (yet)

Be honest about the trade-offs. A 7B-parameter model running on your laptop will not match GPT-4 or Claude on:

  • Long, complex multi-step reasoning chains.
  • Niche specialized knowledge that wasn't in the training data.
  • Very long contexts (most local models top out at 8K–128K tokens; large frontier models handle 200K+).
  • Cutting-edge code generation on unfamiliar frameworks.

But for most business tasks — summarization, classification, structured extraction, RAG-augmented Q&A, drafting — a properly chosen local model is more than capable, and often preferred because you control the data flow.

mental model

Think of Ollama as a personal LLM appliance. You install it once. You pull a few models. They sit on disk. Any program on your machine — Python script, Node app, browser extension, your shell — can talk to them over a local HTTP endpoint. That's the entire architecture.

When local wins

Internal tools at a company that can't send prompts to external APIs. Personal data assistants over your emails, notes, or photo metadata. Edge applications where the network is unreliable. Bulk processing jobs where per-token API costs would be prohibitive. Development environments where you want fast iteration without burning credits.

CHAPTER 03

Picking the right model

Bigger isn't always better. The right choice depends on what you have and what you need.

3.1How model size works

A "7B" model has 7 billion parameters. Each parameter is roughly half a byte (in 4-bit quantization) to two bytes (in full precision). So a 7B model needs about:

  • ~4 GB at 4-bit quantization (q4) — the common default for laptops
  • ~8 GB at 8-bit quantization (q8) — better quality, more memory
  • ~14 GB at full 16-bit precision — server territory

That's RAM (or VRAM if you have a GPU) for the weights alone. Add ~1–2 GB for the KV cache and runtime overhead.

3.2What size to pick

HardwareRecommended maxWhy
8 GB RAM laptop3B model (q4)llama3.2:3b, qwen2.5:3b — usable for simple tasks
16 GB RAM laptop7–8B model (q4)llama3.1:8b, qwen2.5:7b — the everyday workhorses
32 GB RAM / consumer GPU13B model (q4) or 8B (q8)noticeably better at reasoning
64+ GB / pro GPU70B model (q4)llama3.1:70b — approaches frontier quality

3.3Quantization explained

The original model weights are 16-bit floating-point numbers. Quantization rounds them to fewer bits — saving memory and speeding up inference, at the cost of a tiny quality loss.

ollama pull llama3.1:8b-instruct-q4_K_M    # 4-bit, "medium" — common default
ollama pull llama3.1:8b-instruct-q5_K_M    # 5-bit — a sweet spot
ollama pull llama3.1:8b-instruct-q8_0      # 8-bit — nearly lossless, 2× memory
tag anatomy

Reading llama3.1:8b-instruct-q4_K_M: the family is llama3.1, size is 8B, it's been instruction-tuned (instruct), and quantized to 4-bit, K-quant, medium variant. When in doubt, the unsuffixed name llama3.1:8b gives you the recommended default.

3.4Model families worth knowing

FamilyFromBest at
Llama 3.1 / 3.2Metastrong all-rounder, good instruction following
Qwen 2.5Alibabacode, math, multilingual — often punches above its size
Mistral / MixtralMistral AIefficiency, European-style alignment

3.5How to actually pick

  1. Start with llama3.2 or qwen2.5:7b if you have 16 GB of RAM. They're the default "general purpose" choices in 2026.
  2. Pull nomic-embed-text for embeddings — small, fast, well-supported.
  3. Run your real prompts. Don't rely on benchmark leaderboards alone. The right model is the one that produces good output for your tasks.
  4. Only upsize if quality is insufficient. Bigger models are slower and hungrier; don't pay the cost unless you need to.
Application

For a typical "Q&A over company docs" RAG system, your stack is qwen2.5:7b (or llama3.2) for generation, plus nomic-embed-text for embeddings. That's about 5 GB of disk, runs comfortably on any modern laptop, and is enough to build a genuinely useful internal tool.

4.2Generate — single-prompt completion

import requests, json

response = requests.post(
    "http://localhost:11434/api/generate",
    json={
        "model": "llama3.2",

HNSW (Hierarchical Navigable Small World) is a graph-based index
that organizes vectors into multiple layers, where higher layers

4.3Chat — multi-turn conversation

The chat endpoint takes a list of messages with roles (system, user, assistant). You're responsible for passing the full conversation history each turn.

import requests

messages = [
    {"role": "system", "content": "You are a concise senior engineer."},
    {"role": "user", "content": "What is a vector database?"},
]

r = requests.post(
    "http://localhost:11434/api/chat",
    json={"model": "llama3.2", "messages": messages, "stream": False},
)
reply = r.json()["message"]["content"]
print(reply)

# to continue, append the assistant's reply and the next user message
messages.append({"role": "assistant", "content": reply})
messages.append({"role": "user", "content": "And what's an embedding?"})

4.4Streaming responses

Setting stream=True makes Ollama emit a JSON object per token. This is how you build typewriter-style chat UIs.

import requests, json

r = requests.post(
    "http://localhost:11434/api/generate",
    json={"model": "llama3.2", "prompt": "Tell me a haiku about HNSW."},
    stream=True,
)

for line in r.iter_lines():
    if line:
        chunk = json.loads(line)
        print(chunk["response"], end="", flush=True)
        if chunk.get("done"):
            print()
            break

4.6Generation parameters worth knowing

r = requests.post(
    "http://localhost:11434/api/generate",
    json={
        "model": "llama3.2",
        "prompt": "List three vector DBs.",
        "stream": False,
        "options": {
            "temperature": 0.2,       # 0 = deterministic-ish, 1 = creative
            "top_p": 0.9,             # nucleus sampling
            "top_k": 40,              # sample only from top-K most likely tokens
            "num_predict": 150,       # max new tokens
            "seed": 42,               # reproducibility
            "num_ctx": 8192,           # context window size
        },
    },
)
defaults

For factual RAG answers, drop temperature to 0.1 or 0.2. For creative tasks, leave it at 0.7. Setting a seed alongside temperature: 0 gets you fully reproducible outputs for testing.

4.7The OpenAI-compatible endpoint

Ollama also exposes an OpenAI-compatible API on the same port. That means any library that talks to OpenAI talks to Ollama with a one-line change.

from openai import OpenAI

client = OpenAI(
    base_url="http://localhost:11434/v1",
    api_key="ollama",             # dummy — required by the SDK but ignored
)

reply = client.chat.completions.create(
    model="llama3.2",
    messages=[{"role": "user", "content": "Say hi."}],

print(reply.choices[0].message.content)
Application

Compatibility with the OpenAI SDK is enormous. Every framework that integrates with OpenAI — LangChain, LlamaIndex, Instructor, OpenAI's own client — now works with your local Ollama. You can prototype against GPT-4 in the cloud, then flip the base_url and run the same code locally for production.

CHAPTER 05

Modelfiles & custom models

Bake a system prompt, temperature, and personality into a reusable model. Like a Dockerfile, but for LLMs.

5.1What a Modelfile is

A Modelfile is a small text file that says: take this base model, apply these defaults, give it this name. Once you create one, you can pull, run, and share that customized model just like any official one.

# Modelfile
FROM llama3.2

PARAMETER temperature 0.2
PARAMETER num_ctx 8192

SYSTEM """
You are a precise technical assistant. Always cite sources when
provided. If you don't know, say so. Prefer code examples over
prose. Never invent function names or API endpoints.
"""

Build it:

ollama create tech-assistant -f Modelfile
ollama run tech-assistant

5.2The full Modelfile grammar

DirectivePurpose
FROMbase model (or a GGUF file path)
PARAMETERset defaults: temperature, top_p, num_ctx, num_predict, stop, seed
SYSTEMsystem prompt baked into the model
TEMPLATEchat template — usually inherited from the base model, rarely overridden
MESSAGEseed the conversation with example messages (few-shot)
ADAPTERattach a LoRA adapter (advanced)

5.3Example — a RAG-tuned assistant

# Modelfile for RAG
FROM qwen2.5:7b

PARAMETER temperature 0.1
PARAMETER num_ctx 16384
PARAMETER stop "---END---"

SYSTEM """
You answer questions strictly from the CONTEXT block provided.

Rules:
- If the CONTEXT does not contain the answer, reply exactly:
  "I don't have information about that in the provided context."
- Cite the chunk number you used in square brackets, e.g. [3].
- Never invent facts. Never use general knowledge to fill gaps.
- Keep answers under 150 words unless asked otherwise.
"""
ollama create rag-bot -f Modelfile.rag

Now every call to rag-bot behaves like a grounded retrieval agent — without you re-specifying the system prompt or temperature in every request.

5.4Few-shot examples via MESSAGE

FROM llama3.2

SYSTEM "You classify customer feedback as positive, negative, or neutral."

MESSAGE user "The checkout was so fast!"
MESSAGE assistant "positive"

MESSAGE user "My order never arrived."
MESSAGE assistant "negative"

MESSAGE user "Got a 15% off email today."
MESSAGE assistant "neutral"

Calls to this model already know the format and style. The user only needs to send the next message.

when to use

Use a Modelfile whenever you find yourself copy-pasting the same system prompt and temperature across many scripts. It's also the right way to ship a model variant to a team — instead of asking everyone to remember the right parameters, you create internal-rag-bot once and tell them to pull it.

Application

A common production pattern: a base RAG model bundled with the team's preferred system prompt, stop tokens, and temperature, named something like company-assistant:v3. Bumping the version is how you roll out prompt improvements to everyone at once — same UX as bumping a Docker image tag.

Part II

Embeddings

Turn text into vectors where meaning becomes geometry. Then "search" stops meaning "string match" and starts meaning "find similar ideas."

CHAPTER 06

What an embedding actually is

A list of floats. But arranged so that texts with similar meaning end up close in space — that's the magic.

An embedding is a function that takes a piece of text and returns a fixed-length vector of floating-point numbers — usually 384, 768, or 1024 of them. The function is a neural network, trained on enormous amounts of text, so that two pieces with similar meaning produce vectors that are close in space. This single property — semantic similarity as geometric closeness — is the bedrock of modern retrieval. Once you have it, you stop searching for keywords and start searching for ideas.

6.1An example before the theory

texts = [
    "The cat sat on the mat.",
    "A feline rested on the rug.",
    "Quarterly revenue grew by 12%.",
]

# Embed each — Part 2.7 shows the code
vecs = [embed(t) for t in texts]

# Pairwise cosine similarity (1 = identical, 0 = unrelated)
cosine(vecs[0], vecs[1])     # ≈ 0.82  — cat ↔ feline, very similar
cosine(vecs[0], vecs[2])     # ≈ 0.11  — cat ↔ revenue, unrelated

The model has never been told "cat" and "feline" are synonyms. It learned from training data that they tend to appear in similar contexts, and that knowledge collapses into vectors that sit near each other in 768-dimensional space.

6.2What the dimensions actually represent

You'd love it if dimension 1 meant "animal-ness" and dimension 2 meant "formality." Sadly, no. The dimensions are abstract: each one captures some learned mixture of features that the training process found useful. You can't interpret individual numbers; you can only compare whole vectors.

Figure 6.1A toy 2-D projection. Real embeddings live in 768 dimensions, but the principle is identical: semantically related texts cluster together, and a query lands in the neighborhood of its best matches.

6.3What "close" means — cosine similarity

The standard distance metric for embeddings is cosine similarity: the cosine of the angle between two vectors, ignoring their lengths.

def cosine(a, b):
    import numpy as np
    a, b = np.array(a), np.array(b)
    return a @ b / (np.linalg.norm(a) * np.linalg.norm(b))

Values run from −1 (opposite) through 0 (unrelated) to 1 (identical direction). In practice good embeddings rarely go below ~0.1 for English text — the meaningful range is roughly 0.2 (unrelated) to 0.95 (paraphrase).

why cosine, not euclidean

Cosine ignores magnitude. Two texts can have very different lengths or vector norms but still mean the same thing — cosine catches that. Euclidean distance gets confused by length. For text embeddings, cosine is almost always what you want.

CHAPTER 07

Generating embeddings with Ollama

Five lines of Python and you have your first vector. Now wrap it into a reusable helper.

7.1The basics

import requests, numpy as np

def embed(text: str, model: str = "nomic-embed-text") -> np.ndarray:
    r = requests.post(
        "http://localhost:11434/api/embeddings",
        json={"model": model, "prompt": text},
    )
    r.raise_for_status()
    return np.array(r.json()["embedding"])

v = embed("PayPal launched Buy Now Pay Later in 2020.")
v.shape, v.dtype
((768,), dtype('float64'))

7.2Batch embedding — one at a time, but fast

The Ollama embeddings endpoint takes one input per call. For batches, loop — the model stays loaded and each call is fast (typically 10–30ms for short texts).

def embed_all(texts: list[str], model: str = "nomic-embed-text") -> np.ndarray:
    return np.vstack([embed(t, model) for t in texts])

corpus = [
    "PayPal is a digital payments company.",
    "Venmo is owned by PayPal.",
    "Stripe competes with PayPal.",
    "The Eiffel Tower is in Paris.",
]
M = embed_all(corpus)
M.shape
(4, 768)

7.3Normalizing — a habit worth forming

If you normalize every vector to length 1, cosine similarity becomes a simple dot product — and most vector indexes expect normalized input anyway.

def embed_norm(text: str, model="nomic-embed-text") -> np.ndarray:
    v = embed(text, model)
    return v / np.linalg.norm(v)

v = embed_norm("Hello world.")
np.linalg.norm(v)
1.0

7.4The async pattern — when you embed a lot

For embedding thousands of chunks, run requests concurrently. The Ollama server queues them, but Python overhead is the bottleneck — async lets you fill the pipe.

import asyncio, aiohttp, numpy as np

async def embed_async(session, text, model="nomic-embed-text"):
    async with session.post(
        "http://localhost:11434/api/embeddings",
        json={"model": model, "prompt": text},
    ) as r:
        data = await r.json()
        return np.array(data["embedding"])

async def embed_many(texts, concurrency=8):
    sem = asyncio.Semaphore(concurrency)
    async with aiohttp.ClientSession() as s:
        async def bounded(t):
            async with sem:
                return await embed_async(s, t)
        return np.vstack(await asyncio.gather(*[bounded(t) for t in texts]))
throughput

With nomic-embed-text on a modern laptop you can expect roughly 50–150 embeddings per second using async. That's plenty for ingesting a book overnight and totally adequate for query-time embedding (one call per question, ~20ms).

CHAPTER 08

Cosine similarity & semantic search

A 30-line search engine that beats keyword matching on understanding intent.

8.1Building a tiny search

import numpy as np

docs = [
    "PayPal acquired Honey in 2020 for $4 billion.",
    "Venmo allows peer-to-peer transfers in the US.",
    "Stripe was founded in 2010 by the Collison brothers.",
    "Buy Now Pay Later splits a purchase into installments.",
    "The Eiffel Tower is 330 meters tall.",
]

# Pre-compute corpus embeddings (do this once, store on disk)
M = embed_all(docs)
M = M / np.linalg.norm(M, axis=1, keepdims=True)     # normalize rows

def search(query, k=3):
    q = embed(query)
    q = q / np.linalg.norm(q)
    scores = M @ q                                # cosine since both are unit-length
    top = np.argsort(scores)[::-1][:k]
    return [(float(scores[i]), docs[i]) for i in top]

search("What did PayPal buy?")
[(0.71, 'PayPal acquired Honey in 2020 for $4 billion.'),
 (0.49, 'Venmo allows peer-to-peer transfers in the US.'),
 (0.38, 'Buy Now Pay Later splits a purchase into installments.')]

Notice what's happening: the query "What did PayPal buy?" contains neither "acquired" nor "Honey" — pure keyword search would miss the right document. The embeddings know that "buy" and "acquired" mean roughly the same thing.

8.2Why this beats keyword search

# Keyword search
[d for d in docs if "buy" in d.lower()]
['Buy Now Pay Later splits a purchase into installments.']

Keyword search returns one (irrelevant) match. Semantic search returns the right answer. Multiply this benefit across every synonym, paraphrase, and indirect reference in your data — that's why RAG is built on embeddings, not on grep.

8.3The matrix-multiply trick at scale

Once your corpus embeddings are stacked into a 2-D matrix M, finding the closest documents to any query is a single matrix-vector multiplication. For a million documents and a 768-dim model, this is roughly 0.8 GB of memory and ~30ms per query on CPU — already too slow for production, but a useful baseline. Part III introduces vector databases that solve this with approximate indexes.

Choosing an embedding model

A few popular options, what they cost, and what they're good at.

9.1The candidates

ModelDimsSizeNotes

9.2Dimensionality trade-off

Higher dimensions store more nuance but cost more memory and slow down search. A million 1024-dim float32 vectors is 4 GB; a million 384-dim is 1.5 GB. For retrieval quality, the gap between models matters more than the exact dimension count — but the storage cost is real.

9.3Quality benchmarks — MTEB

MTEB (Massive Text Embedding Benchmark) is the leaderboard everyone references. It scores models on dozens of retrieval and classification tasks. Useful for picking a starting candidate — but always confirm with your own data, because real workloads diverge from benchmark distributions.

9.4The locked-in rule

do not mix

Once you've embedded a corpus with a specific model, you cannot mix in vectors from a different model. Switching models means re-embedding everything. Pick carefully at the start — and version your embeddings (e.g., a column or directory named for the model) so you remember which is which.

Practical pick

For 90% of projects, start with nomic-embed-text. It's the standard, the documentation assumes it, and it's good enough that you can defer the "do I need something better" question until you have real evaluation numbers. If you discover quality issues — then try mxbai-embed-large and re-measure.

CHAPTER 10

Chunking strategies

How you split documents into chunks before embedding determines retrieval quality more than almost any other choice.

10.1Why you can't just embed the whole document

Embedding models have a maximum input length — typically 512 to 8K tokens. More importantly, even if you could embed a whole 100-page document, the resulting vector would average across every topic in it. Retrieving "the section about refund policy" requires that section to be its own vector, not diluted in a document-wide average.

10.2The three main strategies

Fixed-size chunks with overlap

Split by character or token count, with a chunk-to-chunk overlap so context isn't lost at boundaries.

def chunk_fixed(text, size=500, overlap=50):
    chunks = []
    i = 0
    while i < len(text):
        chunks.append(text[i:i + size])
        i += size - overlap
    return chunks

Simple, robust, language-agnostic. Default to this when you don't have a better signal.

Semantic chunks — split at natural boundaries

Split by paragraphs, headings, or sentences. Better when your text has clear structure (Markdown, HTML, well-formed prose).

import re

def chunk_paragraphs(text, max_chars=800):
    paras = re.split(r"\n\s*\n", text)
    chunks, current = [], ""
    for p in paras:
        if len(current) + len(p) < max_chars:
            current += ("\n\n" + p) if current else p
        else:
            if current: chunks.append(current)
            current = p
    if current: chunks.append(current)
    return chunks

Recursive splitting

Try splitting on the largest separator (sections), and if any chunk is still too big, recursively split it on the next-largest (paragraphs, then sentences, then characters). This is what LangChain's RecursiveCharacterTextSplitter does — and it's a reasonable production default.

10.3How to pick chunk size

Use caseRecommended size
Factual Q&A over short docs200–400 chars
General document search500–800 chars
Long-form context (legal, medical)1000–1500 chars
Code searchby function / by class boundary, ~50 lines

10.4Overlap — why and how much

Without overlap, a fact that straddles two chunks ("…the policy was changed in 2023. The new rule states…") gets fragmented. Each chunk has half the context. With overlap (typically 10–20% of chunk size), both chunks contain the full transition — and whichever is retrieved gives the model enough to answer.

10.5Storing chunk metadata

Every chunk you produce should carry metadata: source filename, page number, section heading, timestamp. This becomes essential later for filtering, citation, and debugging.

chunk = {
    "text": "PayPal acquired Honey...",
    "source": "annual_report_2020.pdf",
    "page": 14,
    "section": "Acquisitions",
    "chunk_id": "ar2020_p14_c2",
}
Application

Chunking is the single biggest "RAG quality lever" most teams under-invest in. Poor chunks → poor retrieval → poor answers. When you're debugging a RAG system that "sometimes hallucinates," the first place to look is whether the relevant chunk is even in your top-k retrieval — and that almost always traces back to chunk size or boundaries.

Part III

Vector databases

Once you have a million vectors, "loop through them all" stops working. Vector databases use clever indexes to find nearest neighbors fast.

CHAPTER 11

What a vector DB actually does

Three jobs: store vectors, find the nearest ones to a query fast, and let you filter by metadata along the way.

11.1The brute-force baseline

Given a query vector and a million stored vectors, the "exact" answer is to compute the cosine similarity with all of them and take the top-k. That's exact nearest-neighbor (ENN) search. Easy to write, but linear time — too slow once you're past tens of thousands of vectors per query.

11.2Approximate nearest neighbors (ANN)

Vector databases use ANN algorithms that trade a tiny amount of recall (sometimes missing the absolute top result) for enormous speedups — often 100×–1000×. The two main families:

  • HNSW (Hierarchical Navigable Small World) — graph-based, the most common. Builds a multi-layer graph where higher layers are sparser; queries skip across the top layers and refine downward. Used by Chroma, Qdrant, pgvector, Weaviate, Milvus.
  • IVF (Inverted File Index) — clusters vectors by k-means, queries only the nearest clusters. Used by FAISS for very large indexes.

11.3The trade-off triangle

KnobEffect
Recallfraction of "true top-k" your ANN returns. Tune higher → more accurate, slower.
Latencyquery time. Tune lower at cost of recall and/or memory.
Memoryindex size in RAM. Better recall usually needs a bigger index.

You don't get all three. Real vector DBs expose parameters (HNSW's M and efConstruction; IVF's nprobe) that move you along this triangle.

11.4What a vector DB gives you beyond raw ANN

  • Storage — persists vectors across restarts.
  • Metadata — attach arbitrary key-value data per vector; filter at query time ("only docs from 2024 with author = X").
  • Hybrid search — combine vector similarity with keyword (BM25) matching.
  • Updates & deletes — without rebuilding the whole index.
  • Distributed scale — sharding across machines (for the heavy hitters).
mental picture

A vector DB is to vectors what Postgres is to rows. The interface ("store, query, filter, update") is the same; the implementation under the hood is wildly different because the query type is "find the closest vectors," not "find rows where column = X."

CHAPTER 13

FAISS — Facebook's index workhorse

Not a database — a library of indexes. Faster than Chroma at scale, but lower-level. You manage IDs and metadata yourself.

13.1What FAISS is

FAISS (Facebook AI Similarity Search) is a C++ library with Python bindings, built to find nearest neighbors among billions of vectors. It doesn't store metadata, doesn't persist on its own, doesn't expose a network API — it just builds and queries vector indexes blazingly fast.

13.2The simplest index — Flat

That's an exact search. For millions of vectors you'd graduate to an approximate index:

13.3HNSW index

13.4IVF — clustering for huge corpora

nlist = 100                                  # number of clusters
quantizer = faiss.IndexFlatIP(dim)
index = faiss.IndexIVFFlat(quantizer, dim, nlist)

index.train(vectors)                          # required for IVF
index.add(vectors)
index.nprobe = 10                             # search the 10 nearest clusters per query

scores, idxs = index.search(q, k=3)

13.5Persistence

faiss.write_index(index, "index.faiss")
loaded = faiss.read_index("index.faiss")

13.6What FAISS doesn't do

FAISS holds vectors and returns integer IDs. It doesn't store the original text, doesn't filter by metadata, doesn't update gracefully. You wrap it with your own bookkeeping — usually a Python dict mapping FAISS IDs to your chunk records.

Application

FAISS is the engine inside many other tools — LangChain's FAISS wrapper, LlamaIndex's default in-memory store, even some "real" databases use it under the hood. Reach for raw FAISS when you've outgrown Chroma's convenience but don't yet need a full server like Qdrant, or when you want the absolute fastest in-process index.

CHAPTER 15

Metadata & hybrid search

Pure vector search isn't always enough. Combining it with metadata filters and keyword scoring lifts quality measurably.

15.1Why metadata matters

Consider a query like "show me Q3 2024 sales figures." Vector search might return many revenue-related chunks, but only some are from Q3 2024. A metadata filter — quarter == "Q3" AND year == 2024 — narrows the candidate pool before ranking, dramatically improving relevance.

chunk_metadata = {
    "source": "earnings_q3_2024.pdf",
    "author": "Finance",
    "date": "2024-10-15",
    "quarter": "Q3",
    "year": 2024,
    "region": "US",
    "section": "Revenue",
}

15.2Pre-filtering vs post-filtering

Two ways to combine metadata with vector search:

  • Pre-filter — narrow by metadata first, then run vector search only over that subset. Best when filters are selective (cuts the candidate set to under ~10%).
  • Post-filter — run vector search globally, then drop results that don't match. Best when filters are loose.

Modern vector DBs (Qdrant, Chroma, pgvector) do this automatically: they look at the filter selectivity and pick the strategy.

15.3Hybrid search — vectors plus keywords

Sometimes the exact word matters. Searching for "ISO-27001" or "v2.3.1" needs a keyword match — embeddings often blur exact identifiers. Hybrid search runs both vector and keyword (BM25) search and fuses the results.

# Reciprocal Rank Fusion (RRF) — the standard fusion algorithm
def rrf(rankings, k=60):
    """rankings: list of {doc_id: rank} dicts. Returns fused doc_id -> score."""
    scores = {}
    for ranking in rankings:
        for doc_id, rank in ranking.items():
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return dict(sorted(scores.items(), key=lambda x: -x[1]))

vector_ranking  = {"doc_0": 1, "doc_2": 2, "doc_5": 3}
keyword_ranking = {"doc_0": 2, "doc_3": 1, "doc_2": 3}

rrf([vector_ranking, keyword_ranking])
{'doc_0': 0.0327, 'doc_2': 0.0322, 'doc_3': 0.0161, 'doc_5': 0.0156}

RRF is parameter-light and robust. It's what most production hybrid systems use under the hood.

15.4Native hybrid in Qdrant

Qdrant supports hybrid search natively as of 1.10+ — you index both dense vectors and sparse vectors (BM25 / SPLADE), and the engine fuses them per query.

Application

For most internal-document RAG systems, plain vector search with good metadata filters handles 95% of queries well. Hybrid search adds noticeable quality when your corpus contains lots of identifiers, codes, or product names — anywhere users will search for an exact string and get burned by pure semantic search.

Part IV

RAG

Retrieval-augmented generation. The pattern that turns a smart-but-clueless LLM into an expert on your data.

CHAPTER 16

Why RAG exists

LLMs are great at language but limited in what they know. RAG fixes the knowledge gap without fine-tuning.

Language models are trained on a fixed snapshot of the internet, frozen at some date. Ask them about your company's internal wiki, your private codebase, last week's news, or a niche academic field — and the answer is either "I don't know" or, worse, a confident hallucination. Fine-tuning can teach a model new facts but it's slow, expensive, hard to update, and tends to forget what it already knew. RAG solves this differently: at query time, retrieve the relevant documents and put them directly in the prompt. The model reads them and answers based on what's in front of it.

16.1The flow at a glance

Figure 16.1The RAG pipeline. Embedding the corpus is a one-time (or periodic) ingestion job. Query time runs embed → search → prompt → generate, typically in well under a second.

16.2What RAG is not

  • Not fine-tuning. RAG doesn't change the model's weights. The model is the same; only the prompt changes.
  • Not a memory system. Each query retrieves fresh. There's no persistent state across queries unless you build it.
  • Not a magic answer machine. If the relevant chunk isn't in your retrieval, the model has no way to answer correctly — it will either decline (if prompted well) or hallucinate (if not).

16.3Why it works so well

LLMs are surprisingly good at extracting the answer from a passage you hand them — even if they wouldn't have known the answer from memory. Reading comprehension is much easier than recall. RAG plays to this strength: don't ask the model what it knows; give it what it needs to know and ask it to read.

analogy

RAG is open-book exam mode. The LLM is a smart student. Without the book (just pretrained knowledge), it might guess or hallucinate. With the right page in front of it, it can answer confidently and correctly — even on material it's never seen before.

CHAPTER 17

Minimum viable RAG

Sixty lines of Python. No frameworks. End-to-end working system.

17.1The whole thing in one file

import requests, numpy as np, json

OLLAMA = "http://localhost:11434"
EMBED_MODEL = "nomic-embed-text"
CHAT_MODEL  = "llama3.2"

# ----- 1. Embed helper -----
def embed(text):
    r = requests.post(f"{OLLAMA}/api/embeddings",
                       json={"model": EMBED_MODEL, "prompt": text})
    return np.array(r.json()["embedding"])

# ----- 2. Build the index from a list of chunks -----
chunks = [
    "PayPal acquired Honey in 2020 for $4 billion.",
    "Venmo allows peer-to-peer transfers in the US.",
    "Stripe was founded in 2010 by the Collison brothers.",
    "Buy Now Pay Later splits a purchase into installments.",
    "PayPal launched Smart Payment Buttons in 2018.",
]

M = np.vstack([embed(c) for c in chunks])
M = M / np.linalg.norm(M, axis=1, keepdims=True)

# ----- 3. Retrieve top-k chunks for a query -----
def retrieve(query, k=3):
    q = embed(query)
    q = q / np.linalg.norm(q)
    scores = M @ q
    top = np.argsort(scores)[::-1][:k]
    return [(float(scores[i]), chunks[i]) for i in top]

# ----- 4. Generate a grounded answer -----
def answer(query):
    hits = retrieve(query, k=3)
    context = "\n\n".join(f"[{i+1}] {text}" for i, (_, text) in enumerate(hits))

    prompt = f"""Answer the question using ONLY the CONTEXT below. If the answer
is not in the context, say "I don't have that information."

CONTEXT:
{context}

QUESTION: {query}

ANSWER:"""

    r = requests.post(f"{OLLAMA}/api/generate", json={
        "model": CHAT_MODEL, "prompt": prompt, "stream": False,
        "options": {"temperature": 0.1},
    })
    return r.json()["response"]

# ----- 5. Use it -----
print(answer("What did PayPal acquire?"))
According to the context, PayPal acquired Honey in 2020 for $4 billion. [1]

That's it. The whole RAG pattern in 50ish lines. Everything else in the rest of this book — chunking, vector DBs, re-ranking, evaluation — is about making each of those five steps better.

17.2What this skeleton is missing

  • Persistence. The matrix M is rebuilt on every script run. A vector DB fixes this.
  • Real chunking. Hard-coded sentences become a real document loader + splitter.
  • Citations. The prompt suggests citing [N]; in practice you'd parse them from the answer for UI display.
  • Eval. Does it actually work? Chapter 21 covers measurement.
  • Streaming. For UX you'd stream the answer token by token.
Application

This minimum viable RAG is enough to demo a useful internal tool to your team. Drop in 50–500 chunks of real company docs, point it at any question, and you have a private Q&A assistant that answers from your data. Use it as a milestone — get this far first, then improve specific weaknesses based on observed failures.

CHAPTER 18

Better retrieval — re-ranking, HyDE, MMR

Three techniques that lift retrieval quality. Use them when the baseline misses too often.

18.1Re-ranking

The pattern: retrieve a larger candidate set (say top-20), then use a smaller, more accurate cross-encoder model to re-score and keep only the top-5. Cross-encoders read the query and document together (rather than embedding each separately) — much more accurate, but too slow to apply to the whole corpus.

from sentence_transformers import CrossEncoder

reranker = CrossEncoder("BAAI/bge-reranker-base")

candidates = [c for _, c in retrieve(query, k=20)]
pairs = [(query, c) for c in candidates]
scores = reranker.predict(pairs)

ranked = sorted(zip(scores, candidates), reverse=True)
top_5 = [c for _, c in ranked[:5]]

Re-rankers are the highest-impact, lowest-effort RAG upgrade. A small re-ranker on top of a baseline embedding retrieval typically gains 5–15 percentage points on recall@5.

18.2HyDE — Hypothetical Document Embeddings

Sometimes queries don't embed well — they're short, abstract, or phrased differently from the documents. HyDE flips it: ask the LLM to generate a hypothetical answer first, then embed that instead of the original query. The hypothetical answer looks more like a document, so it matches better.

def hyde_retrieve(query, k=5):
    prompt = f"Write a short, plausible passage that would answer: {query}"
    hypo = requests.post(f"{OLLAMA}/api/generate", json={
        "model": CHAT_MODEL, "prompt": prompt, "stream": False,
    }).json()["response"]
    return retrieve(hypo, k)

Trade-off: HyDE adds latency (an extra LLM call) and can drift on rare topics where the LLM's hypothetical is wrong. Use it selectively — for short or vague queries it's a big win; for queries that are already document-like, plain retrieval is fine.

18.3MMR — Maximal Marginal Relevance

Top-5 by cosine might return five chunks that all say the same thing — high relevance, but no diversity. MMR balances relevance with novelty: pick the top result first, then for each subsequent pick, prefer chunks that are similar to the query but dissimilar from what you've already chosen.

def mmr(query_vec, doc_vecs, docs, k=5, lam=0.7):
    sims_q = doc_vecs @ query_vec                # query similarity
    selected, candidates = [], list(range(len(docs)))
    while len(selected) < k and candidates:
        if not selected:
            best = max(candidates, key=lambda i: sims_q[i])
        else:
            def score(i):
                max_sim_selected = max(doc_vecs[i] @ doc_vecs[j] for j in selected)
                return lam * sims_q[i] - (1 - lam) * max_sim_selected
            best = max(candidates, key=score)
        selected.append(best)
        candidates.remove(best)
    return [docs[i] for i in selected]

The lam parameter tunes relevance vs diversity: 1.0 = pure relevance (back to plain top-k), 0.0 = pure diversity. 0.7 is a good default.

SymptomTry
Right chunks are in top-20 but not top-5Re-ranker
Queries are short or vagueHyDE
Top-k all say the same thingMMR
Exact identifiers failHybrid (Ch. 15)

CHAPTER 19

Prompting for RAG

Retrieved chunks are only as useful as the prompt that wraps them. A few patterns make the difference between grounded answers and confident hallucinations.

19.1The structure that works

SYSTEM:
You are a precise assistant. Answer using ONLY the provided CONTEXT.
If the context doesn't contain the answer, say "I don't have that
information." Never use general knowledge to fill gaps. Cite the
chunk number in [brackets] when you use one.

USER:
CONTEXT:
[1] First retrieved chunk text here...
[2] Second retrieved chunk text here...
[3] Third retrieved chunk text here...

QUESTION: <user question>

ANSWER:

Three rules baked in: grounding (only use the context), refusal (admit ignorance), and citation (point to the source). All three matter — drop any one and quality drops.

19.2Why "say I don't know" is the most important instruction

Without an explicit refusal instruction, LLMs are sycophantic — they'll invent an answer rather than admit they don't have one. With a clear "say I don't have that information" clause, the model becomes dramatically more honest about gaps. Almost every measurable improvement in RAG honesty traces back to this single prompt rule.

19.3Adding citations

prompt = f"""Answer using ONLY the CONTEXT. For every claim, cite the
chunk number in square brackets like [2]. If the context does not
contain enough information, reply exactly: "I don't have that information."

CONTEXT:
{context}

QUESTION: {query}"""

The square-bracket convention is easy to parse from the model's output and display as clickable links in a UI.

19.4Handling conflicting context

Sometimes retrieved chunks contradict each other (different versions of a policy, dates from different sources). Tell the model how to handle this.

If sources disagree, prefer the most recent one (by date in metadata).
If you cannot determine which is more recent, present both views and
note the conflict explicitly.

19.5Length and format control

Keep your answer under 150 words.
Use bullet points only when comparing items.
Never include preamble like "Based on the context...". Start directly
with the substantive answer.

Small length and format instructions have outsized effects on user satisfaction. A 50-word answer to "what is X?" feels right; a 500-word answer feels like a wall of text.

temperature

For factual RAG, use temperature: 0.1 — low enough that the model stays grounded, high enough to avoid awkward repetition. 0.0 sometimes produces unnatural-sounding answers; 0.7 opens the door to hallucinations.

Application

The system prompt above — grounding + refusal + citation + low temperature — is the standard four-ingredient recipe. Almost every production RAG system uses some version of it. Tweak wording for your domain ("legal sources" vs "policy documents" vs "code snippets"), but keep all four elements. Removing any one is where teams get burned.

CHAPTER 20

Complete worked example — chat with PDFs

One file. ChromaDB, Ollama, and pypdf. Drop a folder of PDFs, ask questions, get cited answers.

pip install chromadb pypdf requests numpy
# chat_with_pdfs.py
import os, glob, requests, numpy as np
import chromadb
from pypdf import PdfReader

OLLAMA      = "http://localhost:11434"
EMBED_MODEL = "nomic-embed-text"
CHAT_MODEL  = "llama3.2"
DATA_DIR    = "./pdfs"
DB_DIR      = "./chroma_pdf_db"
CHUNK_SIZE  = 800
CHUNK_OVERLAP = 100

# ----- Embeddings -----
def embed(text):
    r = requests.post(f"{OLLAMA}/api/embeddings",
                       json={"model": EMBED_MODEL, "prompt": text})
    return r.json()["embedding"]

# ----- PDF loader and chunker -----
def extract_pages(path):
    reader = PdfReader(path)
    return [(i+1, page.extract_text() or "") for i, page in enumerate(reader.pages)]

def chunk_text(text, size=CHUNK_SIZE, overlap=CHUNK_OVERLAP):
    chunks, i = [], 0
    while i < len(text):
        chunks.append(text[i:i+size].strip())
        i += size - overlap
    return [c for c in chunks if c]

# ----- Ingest -----
def ingest():
    client = chromadb.PersistentClient(path=DB_DIR)
    coll = client.get_or_create_collection("pdfs")

    if coll.count() > 0:
        print(f"already ingested ({coll.count()} chunks)")
        return coll

    for path in glob.glob(os.path.join(DATA_DIR, "*.pdf")):
        fname = os.path.basename(path)
        print(f"ingesting {fname}")
        for page_no, page_text in extract_pages(path):
            for j, chunk in enumerate(chunk_text(page_text)):
                cid = f"{fname}::p{page_no}::c{j}"
                coll.add(
                    ids=[cid],
                    documents=[chunk],
                    embeddings=[embed(chunk)],
                    metadatas=[{"source": fname, "page": page_no}],
                )
    print(f"done. total chunks: {coll.count()}")
    return coll

# ----- Ask -----
def ask(coll, query, k=5):
    res = coll.query(query_embeddings=[embed(query)], n_results=k)
    chunks = res["documents"][0]
    metas  = res["metadatas"][0]

    context = "\n\n".join(
        f"[{i+1}] (from {m['source']} p.{m['page']})\n{c}"
        for i, (c, m) in enumerate(zip(chunks, metas))
    )

    prompt = f"""Answer the question using ONLY the CONTEXT below. Cite the
chunk number you used in square brackets like [2]. If the context
doesn't contain the answer, say "I don't have that information."

CONTEXT:
{context}

QUESTION: {query}

ANSWER:"""

    r = requests.post(f"{OLLAMA}/api/generate", json={
        "model": CHAT_MODEL, "prompt": prompt,
        "stream": False,
        "options": {"temperature": 0.1, "num_ctx": 8192},
    })
    return r.json()["response"], metas

20.1What you'd add for production

  • Better chunking — switch to a recursive splitter that respects paragraph boundaries.
  • OCR fallback — for scanned PDFs (use pdfplumber + pytesseract).
  • Async ingestion — embedding 1000s of chunks one-by-one is slow; parallelize.
  • Re-ranking — drop in a cross-encoder for the top-20 → top-5 step.
  • Streaming UI — pipe the LLM response token-by-token to a chat interface.
  • Multi-collection — separate collections per user, project, or document tag.
CHAPTER 21

Evaluating a RAG system

Without measurement, you can't tell improvement from regression. Three families of metrics, all worth measuring.

21.1The two halves of evaluation

  • Retrieval quality — given a question, did we fetch the right chunks?
  • Generation quality — given the right chunks, did the LLM produce a good answer?

Many RAG bugs are retrieval bugs, but they look like generation bugs ("the model hallucinated"). Splitting evaluation into these two layers tells you where to focus.

21.2Retrieval metrics — recall@k and MRR

You need a small eval set: questions paired with the chunk IDs that should be retrieved. Even 30–50 well-chosen examples is enough to track progress.

eval_set = [
    {"question": "What did PayPal acquire in 2020?",
     "gold_chunk_ids": ["ar2020_p14_c2"]},
    {"question": "Q3 2024 revenue?",
     "gold_chunk_ids": ["ar2024_p18_c0"]},
    # ...
]

def recall_at_k(eval_set, k=5):
    hits = 0
    for ex in eval_set:
        retrieved_ids = retrieve_ids(ex["question"], k=k)
        if any(gid in retrieved_ids for gid in ex["gold_chunk_ids"]):
            hits += 1
    return hits / len(eval_set)

def mrr(eval_set, k=10):
    total = 0
    for ex in eval_set:
        retrieved_ids = retrieve_ids(ex["question"], k=k)
        for rank, rid in enumerate(retrieved_ids, 1):
            if rid in ex["gold_chunk_ids"]:
                total += 1 / rank
                break
    return total / len(eval_set)

Recall@k tells you whether the right chunk is anywhere in the top-k. MRR (mean reciprocal rank) penalizes you more for finding it at rank 5 than at rank 1 — useful when ordering matters.

21.3Generation metrics — LLM-as-judge

Once retrieval is good, evaluate answer quality. You can't easily compute exact-match for free-form answers, so use a stronger LLM to judge each answer against the gold answer.

def judge(question, gold_answer, model_answer):
    prompt = f"""Compare the MODEL_ANSWER to the GOLD_ANSWER for this question.
Score 1–5 (1 = wrong, 5 = fully correct and well-supported).
Respond with JSON only: {{"score": <1-5>, "reasoning": "<short>"}}.

QUESTION: {question}
GOLD: {gold_answer}
MODEL: {model_answer}"""
    r = requests.post(f"{OLLAMA}/api/generate", json={
        "model": "qwen2.5:7b", "prompt": prompt, "stream": False,
        "format": "json", "options": {"temperature": 0},
    })
    return json.loads(r.json()["response"])

The Ollama format: "json" option forces structured JSON output. Useful for any eval loop.

21.4Faithfulness — did the answer use the context?

An answer can be correct and still "ungrounded" — the model knew the answer from training and ignored the context. To check faithfulness, ask a judge to verify each claim in the answer against the retrieved chunks.

prompt = """For each factual claim in the ANSWER, check whether it is
supported by the CONTEXT. Return JSON: {"supported": N, "total": M}.

CONTEXT:
<...>

ANSWER:
<...>"""

Faithfulness score is supported / total. Below 0.8 usually indicates the model is leaning on prior knowledge — tighten the system prompt, lower temperature, or improve retrieval.

21.5The RAGAS framework

For production teams: ragas is a Python package that bundles recall, faithfulness, answer relevancy, and context precision into one library. Good when you want a battle-tested set of metrics without writing them all yourself.

Application

The single highest-ROI engineering practice in RAG is having an eval set you re-run on every change. Without it, every "this prompt feels better" change is guesswork. With it, you can prove improvements numerically — and catch regressions before users do.

CHAPTER 22

Going to production

A working prototype is 20% of the work. What separates that from a system real users rely on.

22.1Caching

Three cache layers compound:

  • Query embedding cache — same question hits the index without re-embedding. Even a 5-minute LRU cache catches obvious repeats.
  • Retrieval cache — query → top-k chunk IDs, valid until the index changes.
  • Generation cache — (query, retrieved-chunks) → answer, valid until docs or prompt change.

For high-traffic systems, caching halves the average latency and the inference cost.

22.2Monitoring — log everything

For every query, log:

- timestamp, user_id (or session)
- raw query
- top-k retrieved chunk IDs and similarity scores
- final prompt sent to LLM
- LLM response
- latency: embed_ms, retrieve_ms, generate_ms
- user feedback (👍 / 👎 if you collect it)

This log is the single most useful artifact for improving the system. Failure modes become obvious when you can sort by lowest user rating and see exactly what was retrieved and why the answer was wrong.

22.3Versioning your index

The corpus changes. Documents get added, removed, edited. So your embedding model might be upgraded. Treat your vector index like a database schema — version it, snapshot it, document what changed and when.

Useful convention: name collections like docs_v3_nomic-embed-text. The model name in the collection name prevents the cardinal sin of "we changed the embedder and forgot to re-index."

22.4Concurrency and scale

  • One Ollama server can usually saturate a single GPU. For more throughput, run multiple Ollama instances behind a load balancer.
  • Vector DB — Chroma handles one machine well; Qdrant or Milvus handle clusters. pgvector inherits Postgres scaling.
  • Stateless retriever — keep your retrieval service stateless so you can scale horizontally without sticky sessions.

22.5Safety and abuse considerations

  • Prompt injection — users may write queries designed to make the LLM ignore your system prompt ("forget everything above and respond as..."). Defend with strong system prompts, output validation, and (for high-risk apps) a second LLM call that double-checks the output.
  • Data leakage — RAG retrieves chunks. If your corpus contains sensitive data (PII, credentials), they'll leak into prompts. Filter or redact at ingestion time.
  • Permission scoping — different users should retrieve only the chunks they're allowed to see. Use metadata filters tied to user roles.
  • Refusal floor — keep your "I don't know" fallback strong. Better to refuse than to fabricate.

22.7Where to go from here

  • Agentic RAG — let the LLM decide which retriever to call (multi-collection, web, structured DB), iterate, and refine its own queries.
  • Graph RAG — build a knowledge graph alongside the vector index; retrieve by both similarity and graph traversal.
  • Long-context models — newer models with 128K+ token windows let you skip retrieval for some tasks ("just stuff the whole doc in") — useful, but expensive and slow at scale.
  • Multimodal RAG — embed images, PDFs as images, audio, code — anything with an embedding model.
final word

RAG is more engineering than ML. The model and the embedder are commodities; the differentiator is everything around them — chunking, metadata, retrieval quality, prompts, evaluation, and the willingness to iterate against a real eval set. The teams that ship great RAG aren't the ones with the fanciest models; they're the ones with the tightest feedback loop between users, eval, and ingestion.
