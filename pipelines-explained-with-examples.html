Chapter 01

What is a Pipeline, Really?

The Core Analogy

A data pipeline is a factory assembly line for information. Raw materials (messy, incomplete, unstructured data) enter one end. Each station on the line does one specific job — clean, reshape, enrich, format. What exits the other end is a finished product your LLM can actually use.

Skip a station and you ship a broken product. The LLM doesn't complain — it just gives you terrible answers and you won't know why.

1.1 Why Raw Data Can't Go Straight to an LLM

The Problem with Raw Data

Imagine you scraped 10,000 customer support tickets to train an LLM to answer questions. Without any cleaning, here's what you'd feed it:

  • Ticket #4821: "hi my refnd didnt work plz help asap!!!! 😤😤😤" — typos, emoji, no context
  • Ticket #4822: "<div class='ticket'>Hello &amp; welcome</div>" — raw HTML tags
  • Ticket #4823:       — 5 spaces, nothing else (null record)
  • Ticket #4824: "CONFIDENTIAL — INTERNAL USE ONLY — Page 3 of 47 — CONFIDENTIAL" — boilerplate repeated on every page
  • Ticket #4825: Duplicate of ticket #3901 word for word

The LLM sees all of this as valid training signal. It learns that "😤😤😤" is normal language. It learns HTML tags are part of sentences. It learns boilerplate is meaningful. The result is a model that gives incoherent, unreliable answers.

A pipeline prevents all of this. Each step removes one category of problem before it reaches the LLM.

1.2 The Mental Model — Five Questions to Ask

📥

Where does data come from?

PDFs, databases, APIs, S3 buckets, web scrapes, spreadsheets. Each source needs its own loader that knows how to extract raw text from that format.

🧹

What's wrong with it?

Every dataset has specific problems. Identify them first: nulls? HTML? duplicates? wrong encoding? Cleaning without knowing the problems wastes time.

⚙️

What shape does the LLM need?

Fine-tuning needs JSONL. RAG needs chunks with metadata. Prompt injection needs a specific format. The pipeline's output depends on how the LLM consumes it.

🔄

How often does data change?

Once-ever documents → batch pipeline. Daily updates → scheduled pipeline. Real-time events → streaming pipeline. The frequency decides the architecture.

📊

How do you know it worked?

Track counts in vs out. Alert on sudden drops. Evaluate LLM quality before and after. A pipeline without monitoring is a time bomb.

🔁

What happens when it breaks?

Which steps can be retried safely? What do you do with half-processed records? Every pipeline needs a plan for failures.

Chapter 02

Where Pipelines Are Used — Real Examples

ℹ️

Every company using an LLM in production runs a data pipeline. The LLM itself is often the smallest part of the system. The pipeline is 70% of the engineering work. Here are 8 real scenarios with exactly how the pipeline works in each.

2.1 Example — Customer Support Bot (PayPal-style)

Real-World Scenario · FinTech Support

🏦 Build an LLM that answers customer questions about refunds, disputes, and policies

The problem: You have 50,000 resolved support tickets, 200 internal policy PDFs, and an FAQ website. You want an LLM chatbot that answers "How long does a refund take?" accurately — not from its training data, but from your actual current policy.

Why a pipeline is needed: The raw tickets contain agent names, internal ticket IDs, phone numbers, copy-paste boilerplate, HTML signatures, and duplicate conversations. The PDFs have headers/footers repeated on every page. None of this should reach the LLM.

1
Ingest — Load tickets from CSV, PDFs from S3

Each ticket becomes one record. Each PDF page becomes text. You now have ~55,000 raw text items.

2
Clean — Remove everything that isn't the actual conversation

Strip HTML email tags. Remove "From: agent@company.com" signatures. Delete "Page 4 of 12" headers. Remove tickets with fewer than 30 words. You now have ~38,000 usable items (31% were noise).

3
Transform — Classify each ticket by intent

Label each: REFUND_STATUS, DISPUTE_OPEN, LOGIN_HELP, etc. This becomes metadata for filtered retrieval later — "only search refund tickets when the user asks about refunds."

4
Chunk — Split long policy PDFs into sections

A 40-page refund policy PDF becomes 80 chunks of ~500 words each, each tagged with the section header as metadata.

5
Deliver — Embed everything into a vector database (RAG)

At query time: user asks "How long does a refund take?" → embed the question → find the 4 most similar policy chunks → inject into the LLM prompt → get a grounded, accurate answer with sources.

2.2 Example — Marketing Email Generator

Real-World Scenario · Marketing Tech

📧 Fine-tune an LLM to write marketing emails in your company's exact voice

The problem: Your marketing team has 3 years of past email campaigns in a CRM. Subject lines, body text, CTAs — all hand-written by your best copywriters. You want an LLM that writes NEW emails in that exact style.

Why a pipeline is needed: The raw CRM export has unsubscribed user emails mixed in, test campaigns with dummy text, bounced emails, emails in 12 different languages when you only want English, HTML formatting codes, and 400 near-identical "Happy Holidays!" emails that would bias the model.

❌ Raw CRM Export (unusable)
  • Subject: "TEST - do not send - TEST"
  • Body: "<p style='color:red'>Click &amp; Save!</p>"
  • Language: Spanish (you only want English)
  • Open rate: 0% (bounced, never delivered)
  • Duplicate: Same email sent 47 times to different lists
✅ After Pipeline (fine-tune ready)
  • Subject: "Save 20% this weekend only"
  • Body: "Hi Sarah, we noticed you loved our summer sale..."
  • Language: English ✓
  • Open rate: 24% (high quality signal)
  • Deduplicated: 1 canonical version kept

The pipeline filters out test emails, strips HTML, detects language (dropping non-English), removes duplicates, and keeps only emails with open rates above 15% — using engagement as a quality proxy. What remains is a curated dataset of high-quality, English, on-brand emails that trains the LLM to write exactly like your best copywriter.

2.4 Example — Medical Record Summarizer

Real-World Scenario · Healthcare AI

🏥 Summarize patient records for doctors before appointments

The pipeline challenge: Medical records come from different hospital systems in different formats — some HL7 FHIR JSON, some scanned PDFs (need OCR), some typed notes, some voice transcripts with disfluencies ("um, the patient, uh, presented with..."). Chapter 03

Ingestion — Getting Data In

Analogy

Ingestion is like a receiving dock at a warehouse. Whatever arrives — pallets, loose boxes, envelopes — the receiving dock's job is to accept it and get it on a shelf in a usable state. It doesn't care what it is; it just unpacks it from whatever container it came in.

In data terms: whether the data is a PDF, a database row, a REST API response, or a Word document, ingestion extracts the raw text and puts it in a uniform format that the next steps can work with.

3.1 Why Different Sources Need Different Loaders

Each format hides text differently

A PDF stores text not as plain sentences but as positioned glyphs on a canvas — "P" at position (72, 120), "a" at (79, 120), "y" at (85, 120). A loader has to reconstruct the reading order. If the PDF was scanned (a photo of a document), there's no text at all — you need OCR (Optical Character Recognition) to detect characters in the image pixels.

A CSV stores each column in a cell. But which column is the "text you want"? The loader needs to know — is it the "description" column? The "body" column? Do you want to combine "title" and "body"? That's a decision you make in the ingestion step.

A REST API returns JSON. But the text you want might be nested three levels deep: response.data[0].attributes.content.body.text. The loader navigates that structure.

3.2 Real Example — Loading a Folder of PDFs (Policy Documents)

python · scenario: PayPal has 200 policy PDFs in an S3 bucketimport pdfplumber, boto3, io

# Step 1: List all PDFs in the S3 bucket
s3 = boto3.client("s3")
bucket = "paypal-internal-policies"
objects = s3.list_objects_v2(Bucket=bucket, Prefix="policies/")

# Step 2: For each PDF, extract text page by page
all_pages = []
for obj in objects["Contents"]:
    key = obj["Key"]
    pdf_bytes = s3.get_object(Bucket=bucket, Key=key)["Body"].read()

    with pdfplumber.open(io.BytesIO(pdf_bytes)) as pdf:
        for page_num, page in enumerate(pdf.pages, 1):
            text = page.extract_text() or ""
            all_pages.append({
                "text":    text,
                "source":  key,           # "policies/refund-policy-2024.pdf"
                "page":    page_num,       # 4
                "doc_type":"policy",      # for metadata filtering later
            })

# Result: list of {text, source, page, doc_type} dicts
# 200 PDFs × avg 15 pages = ~3,000 page records
print(f"Loaded {len(all_pages)} pages from {len(objects['Contents'])} PDFs")
💡

Why track source and page? So later, when the LLM answers "Refunds take 3-5 days," it can cite policies/refund-policy-2024.pdf, page 4. Without this metadata, the answer is unverifiable — users can't trust it.

3.3 Real Example — Loading from a SQL Database

python · scenario: load support tickets from a production databaseimport pandas as pd, sqlalchemy as sa

engine = sa.create_engine("postgresql://readonly_user:pass@db.paypal.internal/support")

# Don't load everything — be surgical about what you need
query = """
    SELECT
        t.id,
        t.subject,
        t.description,
        t.resolution,          -- the answer the agent wrote
        t.category,
        t.created_at,
        a.name AS agent_name   -- we'll REMOVE this later (PII)
    FROM tickets t
    JOIN agents a ON t.agent_id = a.id
    WHERE t.status = 'resolved'       -- only resolved = has a good answer
      AND t.language = 'en'           -- English only for this pipeline
      AND t.created_at > '2023-01-01' -- recent data only
      AND t.quality_score >= 4        -- agent-rated 4/5 or 5/5
    LIMIT 50000
"""
df = pd.read_sql(query, engine)

print(f"Loaded {len(df)} high-quality English tickets")
# Notice: we already filtered at the DB level — faster than loading all and filtering in Python
ℹ️

Key insight: Filter as early as possible. Every row you load costs memory and processing time. Using WHERE quality_score >= 4 in SQL is 10x faster than loading all rows and filtering in pandas.

Chapter 04

Data Cleaning — What, Why & How

Analogy

Cleaning data is like editing a manuscript before publishing. The author (your data source) wrote the first draft. It has typos, repeated sections, footnotes mid-sentence, inconsistent style, and a whole page that's just a legal disclaimer. The editor's job is to produce a clean version that communicates clearly — without changing what the author meant.

4.1 The 6 Types of Dirt — With Real Examples

🗑️ Type 1: Text Noise

What it is: Characters, tags, or formatting codes that have nothing to do with the meaning of the text.

Real example: A PDF exported from Word gives you: "Hello\xa0World\u200b — \t\t see page 3 \n\n\n\n\n"

\xa0 is a non-breaking space. \u200b is an invisible zero-width space. \t\t are tabs. \n\n\n\n\n is 5 blank lines. None of these add meaning. To the LLM, they look like real characters and confuse tokenization.

Fix: Normalize unicode, collapse whitespace, strip invisible chars.

🏷️ Type 2: HTML / Markup Tags

What it is: Web or email systems store content as HTML. When you extract text without parsing the HTML, you get the tags too.

Real example: A customer email stored in a CRM:

<div style="font-size:14px">Hello &amp; thank you for <b>helping</b> me</div>

Becomes: "Hello & thank you for helping me" after HTML parsing. Without cleaning, the LLM sees style="font-size:14px" as content and tries to "understand" CSS.

Fix: Use BeautifulSoup to parse HTML and extract plain text.

📋 Type 3: Boilerplate / Repeated Text

What it is: Text that appears identically on every page (PDF headers/footers) or every record (email signatures, legal disclaimers).

Real example: Every page of a 50-page policy PDF ends with: "CONFIDENTIAL — PAYPAL INC. — Page X of 50 — FOR INTERNAL USE ONLY". That's 50 identical footer strings. If you chunk this PDF into 200 chunks, 50 chunks contain only this boilerplate.

Impact: When a user asks about payment processing, the retrieval system finds these boilerplate chunks as "relevant" (they match on "PayPal") and wastes 25% of the context window on useless text.

Fix: Detect lines that appear in >60% of pages and remove them.

🔁 Type 4: Duplicates & Near-Duplicates

What it is: The same document ingested twice, or very similar documents (like 40 "Happy Holidays" emails) that would over-represent one topic.

Real example: Your company sends the same refund policy to every customer who disputes a charge. You have 8,000 copies of the same paragraph in your ticket database. If you fine-tune on this, the LLM becomes obsessed with refund policy language and applies it to unrelated questions.

Fix: Hash exact duplicates. Use MinHash LSH for near-duplicates (80%+ similar = remove).

🚫 Type 5: Too Short / Low Quality

What it is: Records that are technically valid but too thin to teach the LLM anything useful.

Real examples: Support tickets where the agent wrote: "Escalated.", "Done.", "See above.", "OK ✓". These 1-word "resolutions" are noise — they have a question but no meaningful answer. Fine-tuning on these teaches the LLM that "Escalated." is a valid response to customer questions.

Fix: Filter out records where answer word count < 10 or resolution is a single word.

🔐 Type 6: PII — Personal Information

What it is: Real names, emails, phone numbers, SSNs, account IDs, IP addresses — anything that identifies a real person.

Why it matters: If you fine-tune an LLM on customer support tickets containing real customer emails and account numbers, the model can memorize and later reproduce them. This is a GDPR/CCPA/HIPAA violation and a security incident waiting to happen.

Real example: Ticket: "John Smith (john.smith@gmail.com, account #PP-8823) called about..." → "[PERSON] ([EMAIL], account #[ACCOUNT_ID]) called about..."

Fix: Regex for emails/phones/SSNs + spaCy NER for names, or use Microsoft Presidio.

4.2 Cleaning a Real Support Ticket — Step by Step

python · watch a single messy ticket get cleaned, step by step# The raw ticket from the database:
raw = """From: John Smith <jsmith@gmail.com>
To: support@paypal.com
Date: Mon, 15 Jan 2024 09:23:11 -0800

<html><body>
<p>Hi,  my refnd of $200.00 from<br>transaction PP-88234-2024 hasn't
arrived yet!!!!!!!!</p>
<p>Can&nbsp;you help??</p>
</body></html>

--
John Smith | Senior Manager | PayPal Enterprise Client
Tel: +1-650-555-0192 | john.smith@paypal.com
CONFIDENTIAL: This email may contain privileged information."""

import re
from bs4 import BeautifulSoup
import unicodedata

# Step 1: Strip HTML tags → "Hi, my refnd of $200.00 from transaction PP-88234-2024..."
text = BeautifulSoup(raw, "html.parser").get_text(separator=" ")

# Step 2: Remove email headers (From/To/Date lines)
text = re.sub(r"^(From|To|Date|Subject):.*$", "", text, flags=re.M)

# Step 3: Remove email signature block (everything after "--")
text = re.sub(r"\n--\n.*", "", text, flags=re.S)

# Step 4: Remove CONFIDENTIAL disclaimer
text = re.sub(r"CONFIDENTIAL:.*", "", text, flags=re.S)

# Step 5: Normalize unicode (removes   invisible chars)
text = unicodedata.normalize("NFKD", text).encode("ascii", "ignore").decode()

# Step 6: Redact PII
text = re.sub(r"[\w\.-]+@[\w\.-]+\.\w+", "[EMAIL]", text)
text = re.sub(r"\+?1[-.\s]?\(?\d{3}\)?[-.\s]?\d{3}[-.\s]?\d{4}", "[PHONE]", text)

# Step 7: Collapse whitespace
text = re.sub(r"\s+", " ", text).strip()

print(text)
# Output: "Hi, my refnd of $200.00 from transaction PP-88234-2024 hasn't arrived yet!!
#          Can you help?"
# Clean, no HTML, no email headers, no signature, no PII, single space.

Chapter 05

Transformation — Shaping for the LLM

Analogy

Transformation is like a chef preparing ingredients for a specific recipe. You have clean vegetables (cleaned text). But the recipe (the LLM's input format) calls for diced carrots, not whole ones. You cut them to the right size, season them appropriately, and plate them in the order the recipe specifies. The vegetables haven't changed — they've been shaped for the dish.

5.1 Chunking — The Most Important Transformation

Why chunk at all?

LLMs have a context window limit — they can only "see" a fixed amount of text at once. GPT-4o sees 128,000 tokens max. That sounds like a lot (~96,000 words) but you also need room for your prompt, the question, and the answer. And embedding a 40-page document as one vector is terrible — when someone asks about page 3, the entire 40-page embedding competes with page 3's specific content.

Chunking splits your document into pieces that are:

  • Small enough to retrieve precisely (the right section, not the whole book)
  • Large enough to contain a complete thought (not half a sentence)
  • Overlapping slightly so context at the boundary isn't lost

5.2 Chunking Strategies — Which to Use When

📏 Fixed-Size Chunking

How it works: Split every 1000 characters, overlap 200 characters. Simple.

Real example: A 5,000-char policy paragraph becomes 5 chunks of 1000 chars each, with the last 200 chars of each chunk repeated as the first 200 chars of the next. The overlap prevents losing context at a cut point.

Problem: Can cut mid-sentence. "The refund will be processed within 3-5 business / days depending on your bank." — the split happens mid-phrase.

Use when: You need speed and simplicity. Good default for most text.

📖 Recursive / Sentence-Aware Chunking

How it works: Tries to split at paragraph breaks first, then sentences, then words — never mid-word.

Real example: Same 5,000-char paragraph is first split at \n\n (paragraph breaks). If any piece is still >1000 chars, split again at . (sentence ends). Result: chunks that end at natural boundaries.

Why better: Each chunk is a coherent thought. "The refund will be processed within 3-5 business days depending on your bank." stays together.

Use when: General text documents (default choice for most RAG systems).

📑 Section-Aware Chunking (Markdown/HTML)

How it works: Split at document headings (# H1, ## H2). Each section becomes one chunk, with the heading preserved as metadata.

Real example: A policy doc with sections "Eligibility", "Process", "Timeline", "Exceptions" becomes 4 chunks. Each chunk has metadata {"section": "Eligibility"}. When a user asks about eligibility, the metadata filter immediately focuses retrieval on the right chunk.

Use when: Well-structured docs (wikis, documentation, policy PDFs with clear headings).

👨‍👧 Parent-Child Chunking

How it works: Create two levels — small "child" chunks (200 chars) for precise retrieval, and large "parent" chunks (1500 chars) that provide context. Retrieve by child, return the parent.

Real example: You have a 3,000-word product manual. Small chunks retrieve precisely (matching exactly what the user asked). But returning just those 200 chars loses the surrounding context. So you return the 1500-char parent section — giving the LLM enough context to answer properly.

Use when: You need both high retrieval precision AND sufficient context for answers. Best practice for production RAG.

5.3 Why Metadata Matters — A Concrete Example

Real Scenario · Metadata in Action

🏷️ Without metadata, you can't filter. Without filtering, answers mix up topics.

Imagine: Your vector DB has 10,000 chunks from support tickets. 2,000 are about refunds. 3,000 are about login issues. 5,000 are about general account help. A user asks: "How do I get a refund?"

Without metadata: The RAG system searches all 10,000 chunks by semantic similarity. It returns 4 chunks that happen to be similar — maybe 2 refund chunks and 2 login chunks (login questions often contain words like "account" and "issue" which overlap semantically). The LLM's context is polluted with irrelevant info.

With metadata: Each chunk was tagged with {"intent": "REFUND"} during transformation. The query filter is: search only in chunks where intent = REFUND. All 4 retrieved chunks are now relevant. Answer quality doubles.

python · adding metadata that enables filtered retrieval# During transformation, classify and tag each chunk
from openai import OpenAI
client = OpenAI()

def classify_intent(text: str) -> str:
    # Use a cheap fast model just for classification
    r = client.chat.completions.create(
        model="gpt-4o-mini", temperature=0,
        messages=[{"role":"user", "content":
            f"Classify this support text as one of: REFUND|DISPUTE|LOGIN|ACCOUNT|OTHER\nText: {text[:300]}\nClass:"}]
    )
    return r.choices[0].message.content.strip()

# Now each chunk has intent metadata attached
for chunk in chunks:
    chunk.metadata["intent"]    = classify_intent(chunk.page_content)
    chunk.metadata["date"]      = "2024-01"     # when was this written?
    chunk.metadata["doc_type"]  = "policy"      # policy, ticket, faq
    chunk.metadata["word_count"] = len(chunk.page_content.split())

# At query time — filter by intent
results = vectordb.similarity_search(
    query="How do I get a refund?",
    k=4,
    filter={"intent": "REFUND", "doc_type": "policy"}

Chapter 06

Feeding to the LLM — The Three Ways

Analogy

There are three ways to "give knowledge" to a person before an exam:

Direct Injection = Hand them the notes right before the question. They read it fresh. (Good for small, specific, current info.)

RAG = Give them a library card. When a question comes, they go look it up. (Good for large, dynamic, document-based knowledge.)

Fine-tuning = Make them study for months until they memorize the material. (Good for style, behavior, and domain expertise — not facts.)

6.1 Method 1: Direct Injection — Stuffing the Prompt

What it is & when to use it

You take your cleaned, transformed data and put it directly inside the prompt as text. The LLM reads it right now, answers based on it, then forgets it (next request starts fresh).

Best for: Small datasets (<100k tokens). A single document. User-uploaded files. Real-time data like stock prices or weather.

Real example: A user uploads their own PDF contract and asks "Does this contract allow subletting?" You inject the whole PDF text into the prompt: "Here is a contract: [contract text]. Does this allow subletting?"

Limits: Context window. GPT-4o maxes at 128k tokens (~96k words). A 500-page book won't fit. Also costs more — you pay for every token you inject.

python · direct injection examplecontext = """
REFUND POLICY (Updated Jan 2024):
- Standard refunds: 3-5 business days
- Dispute refunds: 10-15 business days  
- Instant refunds: Available for eligible transactions
- International refunds: 5-7 business days additional
"""

prompt = f"""You are a PayPal support agent. Use ONLY the policy below.
If the answer isn't in the policy, say "I don't have that information."

POLICY:
{context}

CUSTOMER QUESTION: How long does an international dispute refund take?
ANSWER:"""

# LLM will answer: "15-22 business days (10-15 for dispute + 5-7 additional for international)"
# Answer is grounded in the policy you injected. No hallucination.

6.2 Method 2: RAG — Retrieve Then Generate

How it works step by step

Your entire knowledge base is pre-indexed as vectors in a database. At query time, your question is also converted to a vector. The vector database finds the 4-5 most semantically similar text chunks. Those chunks are injected into the prompt. The LLM answers from those specific chunks.

Why this is powerful: Your knowledge base can have 1 million documents. You never send all of them to the LLM — only the 4 most relevant. The pipeline's job was to pre-process all of them so they're ready.

6.3 Method 3: Fine-Tuning — Training the Model

What fine-tuning actually does (and doesn't do)

Common misconception: Fine-tuning injects knowledge into the model. This is mostly wrong.

What fine-tuning actually does: It teaches the model how to respond — the style, tone, format, and behavior. It learns patterns from your examples and applies them to new situations.

Real example: You fine-tune on 5,000 PayPal support conversations. The model learns: always open with an apology for the inconvenience, always end with "Is there anything else I can help you with?", always give a numbered step-by-step when instructions are needed, never mention competitor companies. This is behavioral learning.

What fine-tuning won't reliably do: Remember that a specific policy changed on March 15, 2024. Facts that weren't heavily repeated in training can be forgotten or hallucinated. Use RAG for facts, fine-tuning for style.

Chapter 07

Pipeline Types — Batch vs Stream vs On-Demand

7.1 Batch Pipeline — The Nightly Job

Real Example · Batch Pipeline

🌙 Nightly re-indexing of all policy documents

Scenario: PayPal's policy team updates 5-10 policy PDFs every week. You want the support chatbot to always have the latest information. Every night at 2am, a batch pipeline runs and re-processes all changed documents.

How it works: The pipeline checks a hash of every PDF. If the hash changed since last run, it re-processes that file (re-cleans, re-chunks, re-embeds, re-indexes). Unchanged files are skipped. The process takes 20 minutes for all 200 PDFs, running while no one is using the system.

Tools: cron job or Airflow DAG scheduled with CronSchedule("0 2 * * *") (2am every day).

Why batch, not real-time? PDF changes aren't time-critical. A 24-hour lag between "policy updated" and "chatbot knows about it" is acceptable. Batch is simpler and cheaper than real-time.

7.2 Streaming Pipeline — Real-Time Events

Real Example · Streaming Pipeline

⚡ New support ticket created → indexed within seconds → LLM can answer about it

Scenario: Your company has a product incident. 200 customers open support tickets in the next 10 minutes. Your support team wants an LLM that can detect the pattern ("all these tickets are about the payment page error") in real-time to auto-escalate.

How it works: Every time a new ticket is created, it triggers a webhook → the pipeline picks it up from Kafka → cleans and embeds it → inserts into the vector DB → within 5 seconds, the ticket is searchable. A monitoring query runs every 30 seconds looking for sudden topic spikes.

Tools: Apache Kafka (event stream), Flink or Spark Streaming (processing), Qdrant (vector DB with upsert support).

Why streaming, not batch? A 24-hour delay means the incident escalation happens after hundreds more customers are frustrated. The value is in the real-time detection. The added complexity of streaming is worth it here.

7.3 On-Demand Pipeline — User-Triggered

Real Example · On-Demand Pipeline

📄 User uploads a PDF → LLM can answer questions about it in 10 seconds

Scenario: You build a "chat with your document" feature. A user uploads their lease agreement. Within seconds, they can ask "Does my lease allow pets?" and get an accurate answer.

How it works: Upload triggers a FastAPI endpoint → extract text from PDF (pdfplumber) → clean (remove headers, fix encoding) → chunk (split into 500-char pieces) → embed (OpenAI) → store in a temporary per-session vector index → answer questions → delete the index when the session ends.

Why on-demand? There's no pre-existing knowledge base. The pipeline runs specifically for this user's document, and only this document. It takes 5-10 seconds for a typical 20-page PDF.

Tools: FastAPI (endpoint), pdfplumber (extraction), OpenAI (embedding), ChromaDB in-memory (temporary index).

Chapter 08

Common Mistakes & How to Fix Them

⚠️

These are the mistakes almost everyone makes on their first LLM pipeline. Each one looks harmless but silently degrades your LLM's quality in ways that are hard to debug later.

❌ Mistake 1: Cleaning Order Is Wrong

Wrong order: Deduplicate → Remove HTML → Normalize whitespace

Problem: You deduplicate on raw text. Two tickets that are identical in content but differ only in HTML formatting (<b>hello</b> vs <i>hello</i>) are treated as different records. You keep both. Later, after HTML removal, they're identical — duplicates got through.

Correct order:

  1. Remove HTML first
  2. Normalize whitespace/unicode
  3. THEN deduplicate (on truly comparable text)
  4. THEN filter by quality

❌ Mistake 2: Chunk Size Too Small

The mistake: Thinking smaller = more precise = better. Setting chunk size to 100 characters.

What happens: A policy sentence like "Refunds are issued within 3-5 business days provided the transaction was made with a linked bank account and the dispute was resolved in the buyer's favor." gets split into:

  • Chunk 1: "Refunds are issued within 3-5 business"
  • Chunk 2: "days provided the transaction was made with"
  • Chunk 3: "a linked bank account and the dispute was"

None of these chunks contains the complete policy rule. The LLM gets partial context and gives incomplete answers.

Fix: Start with 500-1000 characters. Measure answer quality. Adjust based on results, not intuition.

❌ Mistake 3: No Metadata = No Filtering

The mistake: Indexing all documents without any metadata tags.

What happens: You have 100,000 chunks from 10 different document categories. A user asks a refund question. The RAG system searches all 100,000 chunks. It finds chunks about refunds, but also finds chunks about "dispute resolution" and "chargeback processing" that are semantically similar but answer a different question.

Fix: Tag every chunk with: source file, doc type, topic/category, date, and any domain-specific filters. This costs a few cents in LLM classification calls but saves enormous retrieval noise.

❌ Mistake 4: Fine-tuning When You Need RAG

The mistake: Trying to "teach" the LLM specific facts by fine-tuning it on them.

What happens: You fine-tune the model with "PayPal refunds take 3-5 days" in 500 training examples. The policy changes to 1-3 days. Now your model confidently states the wrong information — you have to re-train to fix it. Meanwhile, a RAG system would just need a 30-second re-index.

Rule of thumb: If the information can change, use RAG. Fine-tune only for behavior/style that doesn't change (like tone, format, persona).

❌ Mistake 5: Sending All Retrieved Chunks Regardless of Score

The mistake: Always returning top-K chunks even when the scores are low (the question doesn't match any document well).

What happens: User asks "What's the weather like?" (completely off-topic). RAG returns 4 chunks about refunds (best match score: 0.31). LLM receives context about refunds and tries to answer the weather question using it — producing confused, irrelevant output.

Fix: Set a minimum similarity threshold. If the best match score < 0.7, don't retrieve at all — let the LLM answer from its own knowledge or say "I don't have information about that."

❌ Mistake 6: Not Testing the Pipeline Output

The mistake: Writing the pipeline, running it once, assuming it worked because no errors were thrown.

What happens: The pipeline ran silently and produced 50,000 chunks. But 30% of them are just boilerplate that wasn't caught. Another 10% are under 20 words (too short). Nobody noticed because there was no quality check step.

Fix: After every pipeline run, print a sample of 10 random chunks and read them. Check word count distribution. Look at the 10 shortest and 10 longest chunks. Build a dashboard with: total chunks, avg word count, null rate, duplicate rate.

Chapter 09

What to Remember — The Mental Checklists

"The LLM is the last 10% of the system. The pipeline is the first 90%. Most LLM failures are pipeline failures."

9.1 Is This Document Everything You Need?

What this guide covers (the fundamentals)

Yes — for building real pipelines for LLM applications, this guide covers all the fundamental concepts. There are more advanced topics (like distributed streaming with Kafka, GPU-accelerated embedding, or multi-modal pipelines for images+text), but those build on these foundations.

The 5 things that make or break any LLM pipeline:

  1. Clean before you chunk. Chunking dirty text just gives you 100 dirty pieces instead of 1.
  2. Metadata is not optional. Without filters, retrieval is a lottery.
  3. Track what enters and exits each step. A silent drop of 30% of records is a bug, not a feature.
  4. Use the right feeding method. RAG for facts. Fine-tuning for style. Direct injection for small/fresh data.
  5. Incremental updates or you'll rebuild forever. Hash every file. Only re-process what changed.

9.2 The Complete Mental Checklist — Print & Keep

✅ Before You Build Any Pipeline — Ask These Questions

  • Source: Where does data come from? What format is it in? How often does it update?
  • Dirt: What specific problems does this data have? (Run a sample inspection before writing any cleaning code.)
  • PII: Does the data contain names, emails, SSNs, or any identifying info? If yes — redact FIRST, before anything else.
  • Quality signal: Can you filter by quality before processing? (open rates, resolution quality scores, word count minimums)
  • Delivery method: RAG (large dynamic knowledge)? Fine-tune (style/behavior)? Direct inject (small/fresh)?
  • Metadata: What filters will users need? Add those as metadata during transformation.
  • Chunking: What's the right chunk size for this data? Smaller for retrieval precision, larger for context richness.
  • Incremental: How do you avoid re-processing everything every time? Hash files, track what changed.
  • Monitoring: What does a healthy run look like? How will you know if it breaks silently?

9.4 The One-Page Summary — Everything That Matters

🏭

Pipeline = Assembly Line

Source → Ingest → Clean → Transform → Deliver. Each stage does one job. If a stage breaks, everything downstream is wrong. Always know your counts at each stage.

🧹

Cleaning Order Matters

Remove HTML → Normalize unicode → Remove boilerplate → Deduplicate → Filter short → Redact PII. Do it in this order every time. Deduplicating before HTML removal misses near-duplicates.

🏷️

Metadata = Retrieval Power

Every chunk needs: source, type, topic, date. These let you filter searches by category. Without them, retrieval is a keyword lottery and answers mix topics.

✂️

Chunk at Sentence Boundaries

1000 chars with 200 overlap is a good default. Never cut mid-sentence. Use recursive splitter by default. Use section-aware splitting for well-structured docs.

🎯

RAG for Facts, Fine-tune for Style

If the info can change → RAG. If it's about behavior/tone/format → Fine-tune. Trying to teach facts via fine-tuning causes hallucinations when facts change.

🔁

Always Go Incremental

Hash every file. Store what was processed. On each run, only process what changed. This turns a 4-hour nightly job into a 10-minute one and makes pipelines maintainable forever.

✅

Is this guide everything you need for pipelines? Yes — for 90% of real-world LLM pipeline work. The remaining 10% is advanced infrastructure (GPU-scale embedding, distributed Kafka streaming, multi-modal pipelines) that you'd learn when you actually hit those scale limits. Start here. Build something. The gaps will reveal themselves naturally.
