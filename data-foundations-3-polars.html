CHAPTER 01

Why Polars exists

Pandas was built in 2008, single-threaded, on top of NumPy. Polars was built fifteen years later, multi-threaded, on top of Apache Arrow — and the difference shows up everywhere.

Polars is a DataFrame library written from scratch in Rust by Ritchie Vink, designed to solve the things pandas struggles with: single-thread execution, eager evaluation that wastes memory, mutable state that breaks composability, and an API that grew organically across fifteen years of additions. The result is a tool that feels like pandas redesigned with the benefit of hindsight — same operations, cleaner expression, and an order of magnitude faster on most workloads.

1.1The four things that make Polars fast

  • Rust core. No Python interpreter overhead during operations. The hot loop is compiled native code.
  • Multithreading by default. A groupby on eight cores uses eight cores. Pandas uses one.
  • Apache Arrow memory. Columnar, cache-friendly, zero-copy interop with other Arrow-based tools (DuckDB, Spark, BigQuery).
  • Lazy evaluation with query optimization. Polars can rearrange your operations — push filters before joins, drop unused columns early, fuse passes — before executing anything.

1.2The benchmark you'll feel

import pandas as pd
import polars as pl
import time

# Same task: groupby + agg over 50M rows
df_pd = pd.read_parquet("sales_50m.parquet")
t = time.perf_counter()
df_pd.groupby("region")["amount"].agg(["sum", "mean", "count"])
print(f"pandas: {time.perf_counter() - t:.2f}s")

df_pl = pl.read_parquet("sales_50m.parquet")
t = time.perf_counter()
df_pl.group_by("region").agg(
    pl.col("amount").sum().alias("sum"),
    pl.col("amount").mean().alias("mean"),
    pl.col("amount").count().alias("count"),
)
print(f"polars: {time.perf_counter() - t:.2f}s")
pandas: 8.12s
polars: 0.41s

About 20× faster, with no tuning, on a default install. That ratio is roughly typical for groupby and join workloads. For other operations the gap is smaller — but Polars is almost never slower than pandas.

1.3What you give up

Be honest. Switching costs are real:

  • Ecosystem. Every Python tutorial assumes pandas. scikit-learn takes pandas (or NumPy). Many internal tools at companies expect pandas DataFrames. You'll need to convert at boundaries.
  • Index. Polars has no row index — only column data and row positions. This is mostly a feature, but if you relied heavily on pandas' index alignment, you'll re-think workflows.
  • API stability. Polars is still pre-1.0 in some areas, and method names occasionally shift. Pandas is the stable, boring choice; Polars is the modern, evolving one.
  • Stack Overflow answers. When you Google a problem, you get 100 pandas answers and 5 Polars ones. The gap is closing fast but still real.

When to learn Polars

Today. Even if you don't switch all your work right away, the patterns you learn from Polars (expressions, lazy, functional pipelines) sharpen your pandas code too. And once your datasets get big enough that pandas hurts, you'll already know the answer.

CHAPTER 02

The mental model — expressions

The one idea that makes Polars Polars. Get this and the rest of the library suddenly looks consistent.

In pandas, you operate on DataFrames directly: df["col"] * 2 computes immediately. In Polars, you build expressions — lazy descriptions of what to compute — and then hand them to the DataFrame to evaluate.

2.1An expression is a recipe, not a value

import polars as pl

expr = pl.col("price") * 2
print(expr)
[(col("price")) * (2)]

That isn't computing anything yet. It's a description: "take the column named price and multiply it by 2." You then hand it to a DataFrame:

df = pl.DataFrame({"price": [10, 20, 30]})
df.select(pl.col("price") * 2)
shape: (3, 1)
┌───────┐
│ price │
│ ---   │
│ i64   │
╞═══════╡
│ 20    │
│ 40    │
│ 60    │
└───────┘

2.2Why this matters

Because expressions are pure data, Polars can:

  • Execute them in parallel. Independent expressions on the same DataFrame run on separate threads automatically.
  • Reorder them for speed. "Filter then sum" can become "sum only the rows that match the filter" if the optimizer notices.
  • Compose them. An expression can be assigned to a variable, passed to a function, reused across multiple frames.

2.3The four expression building blocks

BuilderUse
pl.col("name")reference a column
pl.lit(value)a literal scalar
pl.col("a") + pl.col("b")arithmetic between expressions
pl.col("x").alias("y")rename the result

2.4A worked example

df = pl.DataFrame({
    "product": ["A", "B", "A", "C"],
    "price":   [10.0, 20.0, 15.0, 8.0],
    "qty":     [3, 2, 5, 7],
})

df.select(
    pl.col("product"),
    pl.col("price"),
    (pl.col("price") * pl.col("qty")).alias("revenue"),
    (pl.col("price") * pl.col("qty") * 1.08).alias("revenue_with_tax"),
)
shape: (4, 4)
┌─────────┬───────┬─────────┬──────────────────┐
│ product │ price │ revenue │ revenue_with_tax │
├─────────┼───────┼─────────┼──────────────────┤
│ A       │ 10.0  │ 30.0    │ 32.4             │
│ B       │ 20.0  │ 40.0    │ 43.2             │
│ A       │ 15.0  │ 75.0    │ 81.0             │
│ C       │ 8.0   │ 56.0    │ 60.48            │
└─────────┴───────┴─────────┴──────────────────┘

One .select() with four expressions. Polars runs the four computations in parallel. There's no temporary state, no mutation, no df["revenue"] = ... assignment leaking around.

2.5Compare to pandas

# Pandas — imperative, mutating
df["revenue"] = df["price"] * df["qty"]
df["revenue_with_tax"] = df["revenue"] * 1.08

# Polars — declarative, no mutation
df = df.with_columns(
    revenue=pl.col("price") * pl.col("qty"),
    revenue_with_tax=pl.col("price") * pl.col("qty") * 1.08,
)

with_columns returns a new DataFrame; the old one is unchanged. Mutation isn't even an option — by design.

key insight

An expression is to Polars what a SQL fragment is to a database: a tiny, composable bit of logic that can be optimized and parallelized. You write what you want, Polars decides how. Stop thinking about loops and start thinking about column transformations.

Application

Master pl.col() and you've mastered most of Polars. Every other concept — group_by, joins, windows, lazy — is just contexts in which expressions are evaluated. Same building block, different scope.

CHAPTER 03

DataFrames & Series

The two data structures. Mostly look like pandas. The differences matter.

3.1Creating a DataFrame

df = pl.DataFrame({
    "name": ["Alice", "Bob", "Carol"],
    "age":  [25, 32, 28],
    "city": ["Austin", "Dallas", "Houston"],
})
df
shape: (3, 3)
┌───────┬─────┬─────────┐
│ name  │ age │ city    │
│ ---   │ --- │ ---     │
│ str   │ i64 │ str     │
├───────┼─────┼─────────┤
│ Alice │ 25  │ Austin  │
│ Bob   │ 32  │ Dallas  │
│ Carol │ 28  │ Houston │
└───────┴─────┴─────────┘

Notice the dtype row directly under the column names. Polars displays types prominently because types matter — there's no silent string/int confusion like pandas can have.

3.2Inspection

df.shape         # (rows, cols)
df.columns       # list of column names
df.dtypes        # list of types
df.schema        # {name: dtype} dict-like
df.head()
df.tail()
df.describe()    # summary stats
df.glimpse()     # transposed view — wonderful for wide tables
df.sample(3)
df.estimated_size("mb")
try glimpse

df.glimpse() prints each column on its own row with its dtype and the first few values. For wide tables (50+ columns) this is much more useful than df.head() truncated horizontally.

3.3Series — a column on its own

s = pl.Series("age", [25, 32, 28])
s.dtype, len(s), s.name
(Int64, 3, 'age')

You'll work with Series less than in pandas — most operations stay in DataFrame-and-expression land. But when you need to extract a column for downstream code, df["age"] or df.get_column("age") gives you a Series.

3.4No row index

The single biggest mental adjustment from pandas. Polars DataFrames don't have a row index — rows are just positions. You can add an integer column to act like one if you want, but most pandas operations that relied on the index translate to columns in Polars.

# In pandas — set_index gives lookup by label
df_pd.set_index("customer_id").loc[42]

# In Polars — just filter by column
df.filter(pl.col("customer_id") == 42)

3.5Types are strict

Polars enforces types. There's no "object" dtype that hides whatever. Common types:

TypeDescription
Int8/16/32/64signed integers
UInt8/16/32/64unsigned
Float32/64floating point
BooleanTrue/False
StringUTF-8 text (was Utf8 in older versions)
Categoricaldictionary-encoded strings
Date / Datetimedate and timestamp types
Durationtime deltas
List(inner)variable-length list per row
Structnested records

The List and Struct types are why Polars handles nested data (JSON, parquet with nested fields) much better than pandas.

Application

The strict typing prevents an entire class of bugs you didn't realize you had in pandas — strings that were supposed to be ints, dates parsed as strings, mixed-type columns that silently degrade performance. Polars surfaces these at load time, not three steps into your aggregation.

CHAPTER 04

Reading data

CSV, Parquet, JSON, Excel, databases, Arrow, even cloud storage. Same APIs as pandas, often much faster.

4.1read_csv

df = pl.read_csv(
    "sales.csv",
    separator=";",
    has_header=True,
    null_values=["N/A", "", "-"],
    try_parse_dates=True,             # auto-detect date columns
    schema_overrides={"id": pl.Int32, "price": pl.Float32},
)

Arguments mirror pandas with cleaner names. The biggest difference: Polars' read_csv is multi-threaded by default, often 5-20× faster than pandas on large files.

4.2Parquet, JSON, Excel, databases

pl.read_parquet("data.parquet")
pl.read_json("data.json")
pl.read_ndjson("data.ndjson")              # newline-delimited JSON, common for logs
pl.read_excel("data.xlsx", sheet_name="Q3")
pl.read_database("SELECT * FROM orders", connection="postgres://...")
pl.from_arrow(arrow_table)                # zero-copy from Arrow
pl.from_pandas(pandas_df)                 # interop bridge

4.3Lazy scanning

The same readers have scan_ variants that don't actually load the data — they create a LazyFrame describing the scan. Combined with the optimizer (Ch. 11), this lets you query files larger than RAM.

lf = pl.scan_csv("huge.csv")             # no data loaded yet
result = (
    lf
    .filter(pl.col("amount") > 100)        # predicate pushdown
    .select("customer_id", "amount")      # projection pushdown
    .group_by("customer_id")
    .agg(pl.col("amount").sum())
    .collect()                              # NOW it executes
)

That pipeline never loads the full CSV. Polars reads only the columns it needs and skips rows where amount ≤ 100 during the read.

4.4Writing

df.write_csv("out.csv")
df.write_parquet("out.parquet", compression="zstd")
df.write_ndjson("out.ndjson")
df.write_excel("out.xlsx")
df.write_database("orders_table", connection="postgres://...")
prefer parquet

Same advice as pandas — once you've cleaned data, save as parquet. With Polars + parquet + lazy scanning, you get column-pruning and predicate pushdown for free. A 100GB parquet file queried for two columns and a filter becomes a 5GB read.

CHAPTER 05

Select, filter, with_columns

Three verbs do most of the work. Once you know them, building any pipeline is just stacking them.

5.1select — pick (and compute) columns

df.select("name", "age")                       # keep just these
df.select(pl.col("name"), pl.col("age"))         # same thing
df.select(pl.all().exclude("city"))             # everything except city
df.select(pl.col(pl.Int64))                     # all integer columns
df.select(pl.col("^.*_id$"))                    # regex on column names

# Select can also compute new columns (rare; usually use with_columns)
df.select(
    pl.col("name"),
    (pl.col("age") * 12).alias("age_in_months"),
)

5.2filter — keep rows matching a condition

df.filter(pl.col("age") > 30)
df.filter(pl.col("city").is_in(["Austin", "Dallas"]))

# Multiple conditions — comma = AND, no parentheses headaches
df.filter(
    pl.col("age") > 25,
    pl.col("city") == "Austin",
)

# OR — use |
df.filter(
    (pl.col("age") < 30) | (pl.col("city") == "Dallas")
)
no pandas paren-trap

Pandas requires every condition inside & and | to be wrapped in parentheses or the operator precedence bites you. Polars sidesteps it: pass multiple positional args to filter and they're combined with AND automatically. No parentheses, no bugs.

5.3with_columns — add or replace columns

This is the most-used verb in real Polars code. It returns a new DataFrame with extra (or modified) columns.

df.with_columns(
    age_doubled=pl.col("age") * 2,
    age_bucket=(pl.col("age") // 10) * 10,
    is_adult=pl.col("age") >= 18,
)

Multiple expressions, run in parallel, no mutation. If a name already exists, it's replaced; if not, it's added.

5.4The pipeline pattern

Real Polars code chains these together:

result = (
    df
    .filter(pl.col("amount") > 0)
    .with_columns(
        revenue=pl.col("price") * pl.col("qty"),
        month=pl.col("date").dt.month(),
    )
    .select("customer_id", "month", "revenue")
    .sort("revenue", descending=True)
)

Each step is a small, named transformation. The pipeline reads top-to-bottom. The original df is unchanged.

5.5Other verbs worth knowing

MethodEffect
.sort("col", descending=True)sort by one or more columns
.unique()drop duplicate rows
.unique(subset=["id"])drop dups on specific columns
.drop("col")remove columns
.rename({"old": "new"})rename columns
.head(n) / .tail(n)first/last n rows
.sample(n)random rows
.limit(n)alias for head
CHAPTER 06

when / then / otherwise

Branching logic, vectorized. The Polars way to do what pandas does with np.where and np.select.

6.1The basic form

df.with_columns(
    category=pl.when(pl.col("amount") > 1000)
              .then(pl.lit("large"))
              .otherwise(pl.lit("small"))
)

Read it like English: "when amount > 1000, then 'large', otherwise 'small'." The pl.lit() wraps a literal value so Polars treats it as an expression.

6.2Multiple branches — chained when

df.with_columns(
    tier=pl.when(pl.col("amount") > 10000).then(pl.lit("whale"))
          .when(pl.col("amount") > 1000).then(pl.lit("big"))
          .when(pl.col("amount") > 100).then(pl.lit("medium"))
          .otherwise(pl.lit("small"))
)

Conditions are evaluated top-to-bottom; the first match wins. Cleaner than pandas' np.select which takes parallel lists of conditions and choices.

6.3Using column values, not just literals

df.with_columns(
    final_price=pl.when(pl.col("discount_active"))
                  .then(pl.col("price") * 0.8)
                  .otherwise(pl.col("price"))
)

6.4Combined conditions

df.with_columns(
    risk=pl.when((pl.col("amount") > 10000) & pl.col("country").is_in(SUSPICIOUS))
          .then(pl.lit("high"))
          .otherwise(pl.lit("normal"))
)

6.5String and date expression methods

Like pandas' .str and .dt accessors, Polars exposes them on column expressions:

df.with_columns(
    name_clean=pl.col("name").str.strip_chars().str.to_lowercase(),
    name_length=pl.col("name").str.len_chars(),
    is_gmail=pl.col("email").str.contains("@gmail"),
    extracted=pl.col("phone").str.extract(r"(\d{3})-(\d{3})-(\d{4})", 1),

    year=pl.col("date").dt.year(),
    month=pl.col("date").dt.month(),
    weekday=pl.col("date").dt.weekday(),
    days_ago=(pl.date(2025, 1, 1) - pl.col("date")).dt.total_days(),
)
Application

The when/then/otherwise chain is how you do tiered customer scoring, conditional pricing, fraud flagging, and any "categorize based on rules" task. Once it's a habit, you stop reaching for if/else and for loops entirely — branching logic on millions of rows runs as fast as arithmetic.

CHAPTER 07

GroupBy with expressions

Same split-apply-combine pattern as pandas. Different syntax. Far more powerful because the "apply" step accepts arbitrary expressions.

7.1The basic shape

df = pl.DataFrame({
    "region":  ["East", "West", "East", "South", "West", "East"],
    "product": ["A", "A", "B", "A", "B", "A"],
    "sales":   [100, 150, 200, 80, 130, 90],
    "units":   [10, 15, 18, 8, 12, 9],
})

df.group_by("region").agg(
    pl.col("sales").sum(),
)
shape: (3, 2)
┌────────┬───────┐
│ region │ sales │
├────────┼───────┤
│ East   │ 390   │
│ West   │ 280   │
│ South  │ 80    │
└────────┴───────┘

7.2Many aggregations at once

df.group_by("region").agg(
    pl.col("sales").sum().alias("total_sales"),
    pl.col("sales").mean().alias("avg_sales"),
    pl.col("sales").count().alias("n_orders"),
    pl.col("units").sum().alias("total_units"),
)

Cleaner than pandas' named-aggregations — every aggregation is just an expression with an .alias().

7.3Conditional aggregation — the killer feature

Because the agg step accepts arbitrary expressions, you can do things that need apply in pandas:

df.group_by("region").agg(
    total_sales=pl.col("sales").sum(),
    sales_of_product_a=pl.col("sales").filter(pl.col("product") == "A").sum(),
    largest_order=pl.col("sales").max(),
    n_unique_products=pl.col("product").n_unique(),
    top_product=pl.col("product").mode().first(),
)
shape: (3, 6)
┌────────┬─────────────┬────────────────────┬───────────────┬───────────────────┬─────────────┐
│ region │ total_sales │ sales_of_product_a │ largest_order │ n_unique_products │ top_product │
├────────┼─────────────┼────────────────────┼───────────────┼───────────────────┼─────────────┤
│ East   │ 390         │ 190                │ 200           │ 2                 │ A           │
│ West   │ 280         │ 150                │ 150           │ 2                 │ A           │
│ South  │ 80          │ 80                 │ 80            │ 1                 │ A           │
└────────┴─────────────┴────────────────────┴───────────────┴───────────────────┴─────────────┘

Look at sales_of_product_a: a filter inside an aggregation. That's a conditional sum per group, written naturally. Pandas can do it, but you need a workaround like df[df.product == "A"].groupby("region").sum() — different DataFrame, separate operation.

7.4Multi-column grouping

df.group_by(["region", "product"]).agg(
    pl.col("sales").sum()
)

7.5Sort grouped output

df.group_by("region", maintain_order=True).agg(
    pl.col("sales").sum()
)

By default, group order is unpredictable (it's determined by the parallel hash). Pass maintain_order=True to keep the order of first appearance — slightly slower but stable.

7.6Lists per group — the gateway to anything

df.group_by("region").agg(
    all_products=pl.col("product"),                # default: collect to list
    products_str=pl.col("product").str.join(", "),
    sales_list=pl.col("sales"),
)

Without an aggregator, a column becomes a List type per group. Then you can apply List operations or explode back to rows. This is the escape hatch for anything weird.

Application

Once you've seen pl.col("x").filter(...).sum() in a group_by agg, pandas groupby starts feeling clumsy. The conditional-aggregate pattern alone replaces dozens of multi-step pipelines. Marketing analytics, cohort analysis, fraud rules — all become natural expressions.

CHAPTER 08

Joins

Same four join types as pandas. Stricter behavior, parallel execution, and a few Polars-specific tricks.

8.1The basic call

customers = pl.DataFrame({
    "customer_id": [1, 2, 3],
    "name": ["Alice", "Bob", "Carol"],
})

orders = pl.DataFrame({
    "order_id": [100, 101, 102, 103],
    "customer_id": [1, 2, 2, 4],
    "amount": [50, 100, 75, 200],
})

orders.join(customers, on="customer_id", how="left")
shape: (4, 4)
┌──────────┬─────────────┬────────┬───────┐
│ order_id │ customer_id │ amount │ name  │
├──────────┼─────────────┼────────┼───────┤
│ 100      │ 1           │ 50     │ Alice │
│ 101      │ 2           │ 100    │ Bob   │
│ 102      │ 2           │ 75     │ Bob   │
│ 103      │ 4           │ 200    │ null  │
└──────────┴─────────────┴────────┴───────┘

Notice null instead of NaN — Polars distinguishes null (missing) from NaN (not-a-number). For text and integer columns, you get proper nulls, not floating-point NaN sentinels.

8.2The join types

how=Result
"inner"only rows matched in both
"left"all left rows; right fills with null where unmatched
"right"mirror of left
"full"everything from both, null where unmatched (was "outer")
"semi"left rows where a match exists (no right columns)
"anti"left rows where no match exists
"cross"cartesian product

Semi and anti joins are wonderful: "give me orders where the customer is in my VIP list" (semi) or "give me orders where the customer is NOT in my fraud list" (anti). Pandas can express these but requires extra steps.

# Anti join — orders from customers NOT in our table
orders.join(customers, on="customer_id", how="anti")
shape: (1, 3)
┌──────────┬─────────────┬────────┐
│ order_id │ customer_id │ amount │
├──────────┼─────────────┼────────┤
│ 103      │ 4           │ 200    │
└──────────┴─────────────┴────────┘

8.3Different key names

orders.join(customers, left_on="customer_id", right_on="id")

8.4Multi-key join

a.join(b, on=["region", "product"])

8.5Validation

orders.join(customers, on="customer_id", validate="m:1")
# raises if customer_id is not unique in customers

Same idea as pandas' validate argument, shorter syntax: "1:1", "1:m", "m:1", "m:m".

8.6Concatenating frames — vertical and horizontal

pl.concat([a, b], how="vertical")         # stack rows
pl.concat([a, b], how="horizontal")       # side by side (same row count)
pl.concat([a, b], how="diagonal")         # vertical, filling missing columns with null

The "diagonal" variant is excellent for stacking files that have mostly the same columns but not exactly — common when ingesting historical data where schemas drifted.

8.7asof joins — time-based matching

For time-series data, join_asof matches each left row to the most recent right row before it. Crucial for things like attaching the latest price snapshot to each trade.

trades.sort("timestamp").join_asof(
    prices.sort("timestamp"),
    on="timestamp",
    by="symbol",
    strategy="backward",        # match to latest price <= trade time
)
Application

The semi/anti joins replace a class of "I need to filter A by what's in B" patterns that pandas usually does with merge + boolean check. asof joins replace a category of hand-rolled "find latest record" code that's slow and bug-prone. Both belong in your standard toolkit.

CHAPTER 09

Reshape — pivot & unpivot

Wide to long, long to wide. Same idea as pandas. Different names, cleaner API.

9.1pivot — long to wide

sales = pl.DataFrame({
    "region":  ["East", "East", "West", "West", "South", "South"],
    "product": ["A", "B", "A", "B", "A", "B"],
    "sales":   [100, 200, 150, 130, 80, 110],
})

sales.pivot(
    on="product",        # values become column names
    index="region",      # stay as row identifiers
    values="sales",
    aggregate_function="sum",
)
shape: (3, 3)
┌────────┬─────┬─────┐
│ region │ A   │ B   │
├────────┼─────┼─────┤
│ East   │ 100 │ 200 │
│ West   │ 150 │ 130 │
│ South  │ 80  │ 110 │
└────────┴─────┴─────┘

9.2unpivot (formerly melt) — wide to long

wide = pl.DataFrame({
    "region": ["East", "West", "South"],
    "A": [100, 150, 80],
    "B": [200, 130, 110],

wide.unpivot(
    index="region",

    variable_name="product",

)
shape: (6, 3)
┌────────┬─────────┬───────┐
│ region │ product │ sales │
├────────┼─────────┼───────┤
│ East   │ A       │ 100   │
│ West   │ A       │ 150   │
│ South  │ A       │ 80    │
│ East   │ B       │ 200   │
│ West   │ B       │ 130   │
│ South  │ B       │ 110   │
└────────┴─────────┴───────┘

9.3Explode — one row per element of a list

Polars has first-class List columns. To unfold a list column into multiple rows:

df = pl.DataFrame({
    "user": ["alice", "bob"],
    "tags": [["red", "blue"], ["green"]],
})
df.explode("tags")
shape: (3, 2)
┌───────┬───────┐
│ user  │ tags  │
├───────┼───────┤
│ alice │ red   │
│ alice │ blue  │
│ bob   │ green │
└───────┴───────┘

The inverse of explode is group_by(...).agg(pl.col("tags")) — collect back into lists.

9.4Transpose

df.transpose(include_header=True, header_name="variable")

Less common than pivot, but useful for quick "rotate this small table" jobs.

CHAPTER 10

Window functions with .over()

Per-group computations that keep every original row. Pandas does this with groupby().transform(); Polars does it more naturally with .over().

10.1The pattern

df = pl.DataFrame({
    "region":  ["East", "East", "West", "West", "South"],
    "product": ["A",    "B",    "A",    "B",    "A"],
    "sales":   [100,    200,    150,    130,    80],
})

df.with_columns(
    region_total=pl.col("sales").sum().over("region"),
    share_of_region=pl.col("sales") / pl.col("sales").sum().over("region"),
    rank_in_region=pl.col("sales").rank(descending=True).over("region"),
)
shape: (5, 6)
┌────────┬─────────┬───────┬──────────────┬─────────────────┬────────────────┐
│ region │ product │ sales │ region_total │ share_of_region │ rank_in_region │
├────────┼─────────┼───────┼──────────────┼─────────────────┼────────────────┤
│ East   │ A       │ 100   │ 300          │ 0.333           │ 2.0            │
│ East   │ B       │ 200   │ 300          │ 0.666           │ 1.0            │
│ West   │ A       │ 150   │ 280          │ 0.535           │ 1.0            │
│ West   │ B       │ 130   │ 280          │ 0.464           │ 2.0            │
│ South  │ A       │ 80    │ 80           │ 1.0             │ 1.0            │
└────────┴─────────┴───────┴──────────────┴─────────────────┴────────────────┘

Every original row preserved. Three new columns computed per-group. One pass, parallelized. This is the equivalent of SQL window functions and it's a joy to use.

10.2Multiple grouping columns

df.with_columns(
    rank_in_region_product=pl.col("sales").rank().over(["region", "product"])
)

10.3Cumulative within groups

df.with_columns(
    running_total=pl.col("sales").cum_sum().over("region"),
    lag_1=pl.col("sales").shift(1).over("region"),
    lead_1=pl.col("sales").shift(-1).over("region"),
)

10.4Rolling windows

df.sort("date").with_columns(
    rolling_7d=pl.col("sales").rolling_mean(7).over("product")
)

Rolling mean of the last 7 days, per product. Three concepts in one line.

10.5Why .over() beats pandas transform

Pandas' groupby().transform() requires you to first select a column and then transform — you can't easily reference multiple columns inside the transform. Polars' .over() is just a modifier on any expression. You can write arbitrarily complex per-group calculations:

df.with_columns(
    weighted_avg=((pl.col("sales") * pl.col("weight")).sum() /
                  pl.col("weight").sum()).over("region")
)
Application

.over() is the operation you'll miss the most if you ever go back to pandas. Customer-cohort analysis, leaderboard ranking, percent-of-total per segment, leads and lags by partition — all become one-liners. SQL users will recognize this as a window function and feel at home immediately.

CHAPTER 11

Lazy mode & the optimizer

Where Polars stops being "pandas but faster" and starts being something fundamentally different. The optimizer turns your query plan into the most efficient execution it can find.

11.1Eager vs lazy

Every Polars operation has two forms:

  • Eager — pl.read_csv(), df.filter(). Computes immediately, returns a DataFrame.
  • Lazy — pl.scan_csv(), lf.filter(). Builds a query plan, returns a LazyFrame. Nothing executes until you call .collect().

11.2What lazy gets you

Figure 11.1The lazy optimizer rearranges your operations. Filters get pushed to the file scan; only needed columns get read; joins happen on already-shrunk data. You don't write the optimization — you just write what you want.

11.3Using lazy mode

lf = pl.scan_parquet("sales_2024.parquet")

result = (
    lf
    .filter(pl.col("amount") > 100)
    .join(pl.scan_parquet("customers.parquet"), on="customer_id")
    .group_by("region")
    .agg(
        total=pl.col("amount").sum(),
        n=pl.col("order_id").count(),
    )
    .sort("total", descending=True)
    .collect()                          # <- materialize
)

Without .collect(), none of those operations actually run. The optimizer sees the whole plan and decides how to execute it.

11.4Inspecting the query plan

lf.explain()                                # text query plan
lf.explain(optimized=True)                 # after optimization
lf.show_graph()                             # visual (needs graphviz)
SORT BY [col("total")]
  AGGREGATE
    [col("amount").sum().alias("total"), col("order_id").count().alias("n")] BY [col("region")]
    FROM
    INNER JOIN ...
      LEFT PLAN ON: [col("customer_id")]
        FILTER [(col("amount")) > (100)] FROM
          Parquet SCAN sales_2024.parquet
          PROJECT 4/12 COLUMNS
          SELECTION: [(col("amount")) > (100)]

The PROJECT 4/12 COLUMNS line shows projection pushdown — only 4 of the 12 parquet columns were read. The SELECTION: line shows predicate pushdown — the amount > 100 filter happened at the file scan, not after.

11.5Streaming — out-of-memory data

For data that's too big to fit in RAM even after filtering, use collect(engine="streaming") or write directly to disk:

(
    pl.scan_parquet("terabyte_dataset/*.parquet")
    .filter(pl.col("event_type") == "purchase")
    .group_by("user_id")
    .agg(pl.col("amount").sum())
    .sink_parquet("purchases_by_user.parquet")    # streams to disk
)

Polars processes the data in chunks, never holding the whole thing in memory. With this, a laptop can crunch through datasets larger than its RAM.

11.6Eager-to-lazy and back

df = pl.DataFrame(...)
lf = df.lazy()                                # convert to lazy
df2 = lf.collect()                              # back to eager

Build interactively in eager mode, then convert to lazy for the final pipeline. You get the best of both: fast iteration during development, optimized execution in production.

when to use lazy

For any pipeline reading from disk and producing a smaller result, prefer scan_* + .collect() over read_*. For quick exploration in a notebook, eager mode is fine. As your pipelines mature, lazy becomes the default.

Application

Lazy mode + scan_parquet is the unlock that lets you query 100GB datasets on a 16GB laptop. The optimizer figures out which columns you actually need and reads only those. Predicate pushdown means filters happen during the file read. It's the difference between "I need to spin up Spark" and "I'll run it on my laptop and grab coffee."

CHAPTER 12

End-to-end & when to choose

The same task as the pandas book, rewritten in Polars. Then guidance for picking which tool to use.

12.1The same pipeline

"Top 5 customers by revenue per region in Q3 2024, with their favorite product." Three CSVs in, one parquet out.

import polars as pl

# All lazy — no data loaded until .collect()
orders    = pl.scan_csv("orders.csv", try_parse_dates=True)
customers = pl.scan_csv("customers.csv")
products  = pl.scan_csv("products.csv")

# Clean & enrich
enriched = (
    orders
    .filter(
        pl.col("customer_id").is_not_null(),
        pl.col("amount") > 0,
        pl.col("order_date").is_between(pl.date(2024, 7, 1), pl.date(2024, 9, 30)),
    )
    .join(customers.with_columns(pl.col("region").str.strip_chars().str.to_titlecase()),
          on="customer_id", how="left", validate="m:1")
    .join(products,  on="product_id",  how="left", validate="m:1")
)

# Per-customer rollup, with favorite product as a window operation
per_customer = (
    enriched
    .with_columns(
        product_sales=pl.col("amount").sum().over(["customer_id", "product_name"]),
    )
    .group_by("region", "customer_id", "customer_name")
    .agg(
        revenue=pl.col("amount").sum(),
        n_orders=pl.col("order_id").count(),
        favorite_product=pl.col("product_name")
            .sort_by(pl.col("product_sales"), descending=True)
            .first(),
    )
)

# Top 5 per region
top5 = (
    per_customer
    .with_columns(rank=pl.col("revenue").rank(descending=True).over("region"))
    .filter(pl.col("rank") <= 5)
    .sort("region", "rank")
    .collect()
)

top5.write_parquet("top5_q3_2024.parquet")

Same outcome as the pandas version. The differences:

  • Lazy everything. Three files scanned, two joins, a window function, a filter — none of it actually runs until .collect().
  • Window function instead of merge. "Favorite product" is done with sort_by + first inside an aggregation, no separate join needed.
  • Rank via .over(). Top-5-per-group is one expression — no groupby().head() dance.
  • Faster. On a million-row dataset, this typically runs in a quarter the time of the pandas version, using less memory.

12.2When to use Polars vs pandas

SituationReach for
Quick exploration in a notebookEither — go with what you know
Data fits comfortably in RAM (< 1GB)Pandas — ecosystem advantage outweighs speed
Data is 1-50GB on one machinePolars — the sweet spot
Data is larger than RAMPolars lazy + sink, or DuckDB
Feeding scikit-learn / PyTorchPandas (or convert at the boundary)
ETL pipelinesPolars — speed and memory wins compound daily
Time-series financePolars — asof joins and window functions shine
You need a specific niche libraryPandas — ecosystem still wins on niches

12.3Interop — use both

import polars as pl

# Polars → pandas
df_pl.to_pandas()

pl.from_pandas(df_pd)

The boundary cost is low, especially through Arrow. A common pragmatic pattern: Polars for heavy ETL, convert to pandas only when handing off to a library that requires it.

12.4What to do next

  1. Use it on a real task. Rewrite one pandas script you have today in Polars. Note where it felt different — that's your learning surface.
  2. Read the user guide. It's short, well-written, and free at docs.pola.rs.
  3. Get comfortable with lazy. Force yourself to use scan_* + .collect() for the next few projects. The optimizer becomes a friend.
  4. Move on to visualization. Once you can shape and aggregate data fluently, the next missing piece is visualizing it. Book 4 covers Matplotlib and Seaborn — designed to work seamlessly with both pandas and Polars output.
parting word

Polars is what you'd build if you started over today knowing what pandas got right and what it got wrong. The expression model, immutability, lazy execution, and Rust core compound into a tool that's measurably better at almost everything pandas does. The only real reason to not use it is the ecosystem — and that gap is closing every release.
